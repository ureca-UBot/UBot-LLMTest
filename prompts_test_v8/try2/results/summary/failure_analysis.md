# prompts_test_v8 try2 — `v5_i4ca` 문제점·좋아진 점, 계산 분석 (2026-10-15)

`v5_i4`(v7) 대비 바뀐 것은 **calc_i4 문단 + 출력 맨 앞의 calc 칸(키 접두어)** 뿐이다(answer → evidence → status 실제 순서는 같음, 순서 설명 문장도 둘 다 같음). Ollama 0.40.3 → 0.40.4 차이는 [정리](../interim_summary.md) 4절에서 작다고 확인.

- 입력: 두 run의 `generation.jsonl`(parsed.calc·answer), `llm_judge/<batch>/accuracy.jsonl`, `test_set4r/cases_fixed.csv`.
- 산술 검사: calc·answer 안의 `식 = 값`(괄호·연쇄 등식 포함)을 직접 계산해 맞는지 본 결정론 검사. 오답 사유는 Judge reasoning 정규식 근사(계산 틀림 / 비교·조건 적용 틀림 / 계산 가능한데 보류 / 누락 / 기타).

## 1. 계산 — 좋아졌나?

**결론: 계산 결과 자체는 좋아지지 않았다.** 산술은 원래 거의 맞았고, 틀리는 곳은 "어떤 식을 세우느냐"(질문 해석·값 선택·날짜 변환)인데 calc 칸은 이것을 고치기도 하고 새로 망치기도 해서 상쇄됐다. 대신 **누락**이 크게 늘어 calc 채운 문항 정답이 135 → 111로 떨어졌다.

### 1-1. 산술 자체는 원래 문제가 아니다

| | 식이 있는 문항 (CE·UI·AR) | 식 개수 | 산술 틀림 |
|---|---|---|---|
| v5_i4 answer | 43 | 64 | 1 (UI-0091) |
| v5_i4ck calc | 71 | 107 | 3 + 평균 1 |
| **v5_i4ca calc** | 72 | 110 | **2 + 평균 2** |

- ca 산술 틀림: UI-0017 `(36,000 - 8,800) × 4 = 104,000`(정답 108,800), UI-0095 `(26,000 + 16,500) - 8,800 = 32,500`(정답 33,700), UI-0123·0125 6개월 합계(239,005 · 440,000 — 정답 240,006 · 420,000). **항이 많거나 다섯 자리 덧셈에서 틀린다.**
- v5_i4는 식을 덜 쓰고(43문항) 결과만 말하는 경우가 많아 산술 실수가 덜 드러날 뿐이다. 예: UI-0125 i4는 평균을 "70,000원"으로 바로 썼고(정답), ca는 calc에 식을 쓰다 합계를 틀렸다.

### 1-3. calc 채운 228문항의 뒤집힘

정답 i4 135 → ca 111 (정답→오답 43, 오답→정답 19).

| | 정답→오답 (ca가 틀린 이유) | 오답→정답 (i4가 틀렸던 이유) |
|---|---|---|
| 누락 | **23** — AR 거리 수치 빠짐 15(AR-0012·0017·0018·0066~0076·0144 등), 일부 결과 한계 누락(AR-0151·0155·0157), CE 함께 안내 누락(CE-0131·0134~0136) | 0 |
| 계산 틀림 | 12 | 7 |
| 비교·조건 적용 | 2 | 6 |

#### 고친 것 (calc 덕분으로 보이는 것)
- **합계 먼저 → 할인 한 번(UI-0091·0094·0098)**: i4는 결합 할인 8,800원을 인터넷·IPTV 각각에 빼거나 회선별 금액을 섞었는데, ca는 `(22,000 + 16,500) - 8,800 = 29,700`처럼 식을 세워 맞혔다.
- **경계 날짜 비교(CE-0085)**: `발급일 + 3개월 = 2026-10-02, 방문일 10-01은 이전 → 이내`. i4는 "넘었다"로 반대 결론.
- **조건 판단(CE-0013·0052·0060·0083, UI-0099·0101)**: 비교 결과를 calc에 먼저 적고 결론을 맞춤.
- **UTC → KST(CE-0177)**, **최대 회선 초과(CE-0075)**.

#### 새로 망친 것
- **질문이 값 두 개를 묻는데 식 하나로 합침(UI-0081·0086·0088·0089)**: "해지 전·후 전체 할인 합계"를 묻는데 calc가 `(4 × 8,800) - (3 × 5,500) = 18,700`(차액) 하나를 만들고 answer도 "전체 할인 합계는 18,700원"만 썼다. i4는 35,200원·16,500원을 각각 답했다. **calc는 "최종 결과 하나"로 수렴하게 만든다** — MT에서 두 질문 중 하나만 답하는 현상(정리 3-1절)과 같은 모양이다.
- **값을 잘못 고른 식(CE-0048, UI-0093)**: CE-0048 `32 - 30 = 2`를 "2GB 남습니다"로(실제 초과), UI-0093 할인 8,800원을 두 상품에 각각 뺌.
- **경계·시간 변환(CE-0086, CE-0178)**: CE-0086은 경계일(10-02)을 "이내가 아님"으로, CE-0178은 `15:20 + 9시간 = 23:20`. CE-0177은 고쳤으니 UTC 변환은 **calc 유무와 상관없이 맞았다 틀렸다 한다**(CE-0176은 둘 다 틀림).
- **산술**: UI-0017·0095·0123·0125(1-1절).

#### 둘 다 못 하는 것 (calc로 안 바뀜)
- **만 나이(CE-0094·0098·0100)**: 생일 전후 판단을 calc에 써도 틀린다(`2026 - 2007 = 19세, 10월 4일 이후이므로 19세`).
- **이미 있는 것에 더하기(CE-0149·0150)**: "현재 2개 + 1개 추가 = 3개 > 최대 2개"를 못 함.
- **계산은 맞는데 전제가 틀림(UI-0153~0155·0159, UI-0200)**: 보유 포인트가 없는데 `5,000 - 1,600 = 3,400`을 "쓸 수 있는 포인트"로 확정, 9월 사용량으로 10월 잔여량 계산.
- **잘못된 단가 선택(UI-0012·0014, CE-0076·0077)**: 회선 수에 맞지 않는 할인 단가를 고름.

### 1-4. calc에는 맞는데 answer에 안 옮김

정답 예시의 계산 값(입력에 없는 숫자)이 calc에는 모두 있는데 answer에는 없는 문항 11건(UI-0081·0086·0087·0088·0089·0091·0098·0100, CE-0013·0082, AR-0166). 대부분은 answer가 최종 값 하나만 남기고 중간 값(정답 예시가 요구하는 값)을 버린 경우다. AR은 calc에 거리를 다 써 놓고 answer에서 거리를 뺐다(1-3절 누락 15건).

## 4. 정리

- **계산 정확도는 그대로**다. calc 칸이 "식을 써 보게" 하는 효과는 있어서(합계 후 할인, 경계 날짜) 몇 건 고쳤지만, 같은 수만큼 식을 잘못 세우거나(차액을 합계로, 값을 잘못 고름) 산술을 틀렸다. 만 나이·UTC·"기존 + 추가 ≤ 최대"처럼 원래 못 하던 계산은 calc로도 안 된다.
- 실제 손해는 **누락**이다. calc가 결과 하나로 수렴하게 만들고, "결과만" 문장이 answer를 그 결과 한 줄로 줄였다 — 정답 예시가 요구하는 중간 값(해지 전·후 각각, 거리)과 두 번째 질문을 버린다.
- 다음에 calc를 다시 쓴다면: "결과만" 문장 삭제, "질문이 묻는 값을 모두 calc와 answer에 각각 쓴다", "calc에 쓴 한계·조건도 answer에 쓴다". 계산 자체의 정확도는 프롬프트보다 **계산을 코드로 넘기는 쪽**(백엔드가 할인·잔여량·날짜 비교를 계산해 조회 결과로 넘김)이 확실하다 — 4B 모델이 틀리는 것은 산술보다 식 세우기·날짜 처리다.
