### 4-3. 도구 경로 최종 답변 형식

feat/277은 사용자 정보 조회 도구(getBillingByMonth·getUsageByMonth)와 매장 도구가 붙어 거의 모든 답변이 도구 경로다. 도구 경로에서는 Ollama가 출력 스키마를 강제하지 않는다(v1부터 확인). v6 답변 LLM 호출 182회 중 도구 경로 171회의 최종 형식은 **정상 133 · 칸 수 불일치 35 · 깨짐 3**이었다. 칸 수 불일치는 코드가 칸을 합치거나(`slots_collapsed`, 32건) status를 null로 남긴다. 합친 32건 중 22건은 남는 칸에 청구서·회선·요금제 같은 개인 데이터가 들어 있었고, 합친 32건 중 7건(CQ-008·022, MT-006, SA-023·038·040, UD-015)은 합친 답을 출력 가드가 막았다(4-2절의 SA-023·040). 실행 오류는 UD-025 LLM-005 1건으로 작았지만, 형식 정합을 모델에 맡기는 구조라 → [v7](../../../pipeline_test_v7/try1/results/all_summary.md)에서 최종 답변 스키마 강제를 시험했다.

## 7. 판단과 다음

- **회선 데이터는 평가 기준으로 유지한다.** 실제 사용자 조건에 맞고, 회선 없음 추론 환각(19 → 4)과 고지가 줄었다. 앞으로 feat/277 계열 평가는 이 seed와 v6 케이스셋을 쓴다.
- 정답이 오르지 않은 이유는 두 가지이고, 둘 다 다음 과제다.
  1. **개인 데이터 끌어오기**: 일반 FAQ 질문에도 청구서·요금제·회선 값을 근거로 붙이고 단정한다(UD 밖 44/142건이 개인 데이터 언급). 사용자 정보는 개인 값을 묻는 하위 질문에만 쓰게 하거나(intent별 섹션 부착), 프롬프트에서 "개인 정보는 개인 값을 물을 때만" 기준을 둔다.
  2. **출력 가드의 칸 단위 차단**: 개인 데이터 문장 하나 때문에 맞는 FAQ 사실까지 버린다(SA 5건). 문장 단위 제거나, 차단 시 FAQ 근거 문장만 남기는 처리를 검토한다. 가드 전 답변을 Judge해 가드 정밀도를 재는 것이 먼저다.
- 계산·날짜 오류(UD-006·030)는 "조회 기준일"과 "이번 달 청구서"의 정의를 섹션에 명시하는 쪽으로 다룬다.
- 도구 경로 최종 답변 형식(171회 중 38회 불일치) → [v7](../../../pipeline_test_v7/try1/results/all_summary.md)에서 스키마 강제 두 방식(always · on-broken)을 비교했다.
