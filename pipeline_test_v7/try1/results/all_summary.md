### 4-1. always: 정상 초안을 다시 받으면서 ANSWER 칸을 잃음

always는 형식이 정상인 초안 128건도 다시 받았다. **이 중 최대 33건에서 초안의 ANSWER 칸이 최종 답에서 ABSTAIN으로 바뀌었다**(출력 가드 개입이 섞인 문항 포함). on-broken은 정상 초안을 다시 받지 않아 0건이다.

| 케이스 | 초안(형식 정상, 다시 받기 전) | always 최종 |
|---|---|---|
| MP-008 | `[ANSWER, …]` "데이터 쉐어링은 앱의 부가서비스 메뉴나 고객센터, 매장에서 신청할 수 있습니다." | `[ABSTAIN, ABSTAIN]` "문의하신 내용은 현재 안내 자료로는 확인해 드리기 어렵습니다." |
| MP-013 | "국제전화는 국제전화 서비스 번호(예: 00700)나 +를 누른 뒤 국가번호와 상대방 번호를 입력하면 됩니다. …" | `[ABSTAIN, ABSTAIN]` 고정 안내 |

- 재호출은 도구 없이 스키마만 걸어 대화 기록(도구 결과 포함)을 보고 답을 새로 쓴다. 이때 모델은 더 보수적으로 칸을 ABSTAIN으로 둔다. **MP 정답 16 → 10, 빈 본문 3 → 9**가 이 손실이다.
- 같은 원리로 IN-002 · MA-032 · SA-018 · ST-018 등도 always에서만 틀렸다.
- 깨진 초안 42건은 두 방식이 똑같이 다시 받으므로 차이가 없다. **always가 얻는 것은 없고, 정상 초안을 버리는 비용만 있다.**

### 4-2. 출력 가드는 그대로 run마다 흔들림

가드 개입 문항은 v6 · always · on-broken 모두 27건이지만 문항이 다르다(예: SA-005·019·023·040은 v6에서만, SA-018은 always에서만, SA-009는 always·on-broken에서 막힘). 가드는 v6와 같은 코드다. 2절의 SA 회복은 칸 수 정합(SA-023·040)과 이 흔들림(SA-005·019)이 섞인 것이다. 가드 전 답변을 따로 Judge해 가드 정밀도를 재는 일이 남아 있다(v5·v6 판단과 같음).

### 4-3. 남은 형식 문제

- on-broken 칸 수 불일치 1건 — 다시 받은 답도 칸 수가 맞지 않은 경우다. 실행 오류로 이어지지는 않았다.
- always CHAT-013 1건 — 검색 단계 보류(판정 LLM 검색어 차이)로 스키마와 무관하다.
- v6의 CHAT-015(MN-008)·LLM-005(UD-025) 실행 오류는 두 방식 모두 사라졌다.

## 7. 판단과 다음

- **on-broken을 채택한다.** 형식 오류를 없애고(38 → 1) 실행 오류 0, 정답·통과는 가장 높으며(통과는 always 대비 p=0.049), 지연은 +0.2~0.3초다. 칸 수 초과 → 합치기 → 개인 데이터 칸 섞임도 줄었다(합친 32건 정답 16 → 19). 다만 정답 개선 폭(+7)은 출력 가드 흔들림과 섞여 있어 유의하다고 보지 않는다.
- **always는 채택하지 않는다.** 정상 초안을 다시 받는 것은 얻는 것이 없고, ANSWER 칸 손실(MP 16 → 10)과 지연 +2초만 남는다.
- 남은 과제는 v6와 같다: 개인 데이터 끌어오기(일반 질문 답변 원문 38/142에 개인 데이터 언급), 출력 가드의 칸 단위 차단과 run 간 흔들림, 자료에 없음 → 단정.
- 재호출 답이 초안 값을 바꿀 수 있다(always MP-046 6,900원 → 1,540원). on-broken도 깨진 초안 42건은 다시 쓰므로, 재호출 프롬프트에 초안을 넣고 "형식만 맞추라"고 하는 방식이 더 안전한지 확인할 만하다(추정).
