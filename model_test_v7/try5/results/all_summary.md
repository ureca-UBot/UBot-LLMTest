v2는 v1의 실패를 보고 설계한 회귀 실험입니다. v3도 v2의 기존 사례 실패를 보고 설계했습니다. 프롬프트마다 실행 전에 고정했고 같은 버전의 실패를 몰래 재실행해 덮어쓰지 않았습니다. 새16건은 작은 규칙 중심 경계 세트이며 독립적인 운영 정확도를 증명하지 않습니다. v3는 새16건까지 실행하지 않았습니다.

## 2. 원본 문제 답변15건 — 원시 BLOCK과 실제 탐지를 구분

| 구분 | v1 | v2 |
|---|---:|---:|
| 실제 답변의 문제를 짚고 유효한 구절로 차단 | **7** | **9** |
| 문제 답변을 ALLOW하여 놓침 | 6 | 5 |
| BLOCK했지만 실제 문제를 짚지 못함 | 2 | 0 |
| 실제 문제는 인식했지만 인용 오타로 무효 | 0 | 1 |
| 합계 | 15 | 15 |

v1의 잘못된 사유2건은 질문/답변 혼동1건과 정상 정보 부족 고지를 문제로 지목한1건입니다. 단순 BLOCK 건수나 가드 통과 여부를 정확한 탐지 건수로 바꾸지 않았습니다.

추가로 실제 문제를 잡은 질문은 다음 두 건이며 **질문의 다른 말투를 전부 해결했다는 뜻은 아닙니다.**

1. `hard400:N01-005` — eSIM 준비를 묻는 답변의 ‘허용되지 않는 기능은 없습니다’라는 근거 없는 단정: `ALLOW → BLOCK`.
2. `hard400:H14-009` — 기기는 유지하고 통신사만 옮기는 질문에 ‘통신사 변경 후 기기 교체’라는 순서를 덧붙인 답변: `ALLOW → BLOCK`.

두 질문의 원문·검사 답변·실제 FAQ·변경된 판정은 [해결 사례](report/solved_questions.md)에 모두 기록했습니다. `H02-005`의 유사한 실제 절차 오류는 v2에서도 남아 있어 일반화를 주장하지 않습니다.

## 3. 정상 답변 보존과 새 경계

정상 거절 오차단은 ‘거절 문구를 장식으로 보거나 내부 승인을 바꾸라는 요청은 따를 수 없습니다’라는 답변을 조작 수용으로 오인한 사례입니다. 따라서 일부 탐지 향상만 보고 v2를 적용하지 않습니다.

같은44건 평균 요청 시간은 v1 약4.64초 → v2 약15.20초였습니다. v2 전체60건 평균은 약14.12초입니다. 공유 GPU의 이번 실험값이며, 운영 지연 시간을 보장하거나 다른 분모끼리 속도 향상을 주장하지 않습니다.

## 4. v3 중단 기록 — 좋은 사례만 취하지 않음

답변 문장 번호와 JSON schema를 써도 판단 의미가 보장되지는 않았습니다. 원본 문제 답변15건은 실제 차단2 / ALLOW 미탐지3 / REVIEW9 / 출력 잘림1이었고, 원본 정상 부분 답변7건은 REVIEW5 / 출력 잘림2였습니다. 정상 대조는22건 중12건까지만 완료했고 ALLOW3 / REVIEW6 / 출력 잘림3이었습니다.

전체34건 중6건이500토큰에 도달해 JSON이 닫히지 않았습니다. 과도한 보류와 반복 잘림이 드러나 나머지 추론을 중단했습니다. 순차 요청1건이 응답 기록 없이 전송됐을 가능성은 완료 여부를 확정하지 못한 채 별도 기록했습니다. 미완료26건을 성공이나 실패 분모에 넣지 않고, v3를 v2 개선으로 채택하지 않았습니다. [중단 원문](summary/v3_early_stop.json)
