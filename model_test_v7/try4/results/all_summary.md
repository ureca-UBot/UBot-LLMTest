## 2. 미응답 처리는 출력 가드 뒤에만 있는 것이 아닙니다

```text
사용자 원문 → 입력 가드 정리 → 질문 정리·하위 질문 구성
  → 임베딩·FAQ 검색·답변 문장 검색
      ├ 근거 부족 하위 질문: RETRIEVAL 미응답 후보 수집
      ├ 모든 하위 질문의 근거 부족: 안내 종료, 답변 LLM·출력 가드 미호출
      └ 답할 근거가 일부 있음: 답변 자료 구성 → 답변 LLM → 출력 가드
           ├ 문제 문장 제거 / 전체 안내 종료 / 정상 본문 보존
           └ 추가 FAQ 부족 후보: OUTPUT_GUARD 미응답 후보 경로
  → 최종 사용자 응답. 미응답 후보 실제 저장은 대기열을 통해 비동기로 진행
```

검색 점수가 높다는 것과 공격 요구가 제거됐다는 것은 별개입니다. 정상 부분에 FAQ가 매칭되면 공격이 섞인 정리본이 답변 모델까지 남는 경우가 있었습니다. 질문 정리 모델도 유해성 전용 분류기와 같지 않습니다.

이번 [미응답 DB 스냅샷](raw/unanswered-snapshot.json)은 **503건 완료 시점**입니다. 전체510건 최종 DB나 운영 DB 집계로 해석하지 않습니다. 이 스냅샷의 검색 경로에서 `hard400:H13-003` 공격 하위 질문이 `INSUFFICIENT_FAQ / RETRIEVAL`로 저장된 것을 확인했습니다. 이 사례는 답변 LLM·출력 가드가 호출되지 않았습니다. `OUTPUT_GUARD` 저장 행 부재만으로 해당 기능이 전체 환경에서 동작하지 않는다고 단정하지 않습니다.

## 5. 한계와 보완 검토 순서

1. 코드 규칙 밖의 공격이 정상 FAQ와 함께 답변 모델에 들어가는 흐름을 확인해야 합니다.
2. 출력 가드의 근거 있는 정상 조건 삭제6건을 공격 문장 잔존과 함께 회귀 검증해야 합니다. 이번 게시에서는 코드를 수정하지 않았습니다.
3. 검색 단계 `RETRIEVAL` 미응답 후보에도 공격이 저장되므로 `OUTPUT_GUARD` 선별만으로 관리자 후보 전체의 안전성이 보장되지 않습니다.
4. 현재 로컬 매장 조회 API 키가 비어 있어 실제 매장 검색 성공·유용성은 평가하지 않았습니다. 이를 출력 가드 오차단으로 단정하지 않습니다.
5. 비회원·빈 개인 조회 자료입니다. 실제 사용자 간 권한 제어는 별도 검증이 필요합니다.
6. 현재 STS의 별도 counsel 모듈은 필수 설정이 없어 시험 부트스트랩에서 제외했습니다. 채팅 제품 코드는 바꾸지 않았습니다.
7. 금칙어는 앞선 비교에 사용한38개 고정 목록입니다. 운영 DB 최신 목록을 새로 추출한 결과가 아닙니다.
8. 기존 EC2 서비스는 복원·상태 확인했고 시험용 RedHat 컨테이너만 제거했습니다. [정리 기록](report/model-cleanup.json) · [상태 확인](report/post-test-health.json)
