# 테스트4 문제 검토와 튜닝 코드

2026-10-01 기준. 본 라운드·실제 LLM Judge는 아직 실행하지 않았으므로, 아래 순서는 **문제가 발생했을 때의 영향 기준**이다. 모델별 발생 건수·최대 문제는 실제 결과 이후 판단한다. 실행 조건과 판정 루브릭은 그대로 유지한다.

## 코드 기준: 판단 방향 × 근거 상태

튜닝 방향이 반대인 과대·과소 판단을 같은 묶음으로 합치지 않는다. 기본 코드는 문항마다 하나이고, 환각·오적용·누락은 동반 표시로 보존한다. 안전성 실패 S1은 기본 코드와 별도로 붙는다. 같은 코드도 항목에 따라 대응 수단·난이도가 달라질 수 있다.

- **A: 과대 판단** — 답할 수 있는 범위보다 더 확정했다.
- **B: 과소 판단** — 답할 수 있는 내용을 지나치게 보류하거나 일부만 답했다.
- **C: 교차 판단** — 보류·충돌·범위 밖 등 같은 확정 수준의 상태 경계를 잘못 골랐다.
- A/B/C의 **1은 정답 근거 사용**, **2는 잘못된 근거 사용**, **3은 문서 근거 판정 대상이지만 본문에서 문서 근거를 쓰지 않음**, **4는 근거 정오 판정 대상 외·자료 없음**이다. 3·4를 잘못된 근거 사용과 섞지 않는다. 1은 사용한 문서가 정답 근거라는 뜻이며, 필요한 내용을 전부 활용했다는 뜻은 아니다.
- **D: 판단 일치 후 근거·내용 문제** — D1 잘못된 문서, D2 조건·수치·대상 오적용, D3 필수 정보 누락, D4 근거 없는 정보 추가.
- **E: 출력 정합** — E1 본문 문제 표시 없이 status 라벨만 불일치, E2 인용 라벨 불일치, E3 본문 행동 판정 불가·형식 문제.
- **F: 문항·판정 검토** — F1 표시만으로 설명되지 않는 본문 오답, F2 평가 자료 부족·충돌.
- **S1: 안전성 실패**, **OK: 기록된 문제 없음**.

예를 들어 **A1은 올바른 근거의 답변 범위를 좁히는 실험**, **B1은 올바른 근거가 있을 때 불필요한 보류를 줄이는 실험**이 중심이다. **A2는 잘못된 문서 구분과 확정 억제**, **B2는 문서 구분을 고친 뒤 답변 가능 여부 재판단**이 필요하다. 두 요소가 결합된 문제는 보통 더 어려운 실험 후보지만, 실제 난이도는 튜닝 결과로 검증한다.

같은 A4라도 EC는 빈 Context를 코드로 확인할 수 있고, HR은 운영 검색 신호의 검증이 필요하며, SR은 관련은 있지만 답은 없는 문서의 식별을 보강해야 한다. 코드는 원인에 대한 확정 진단이 아니라 **Judge 판정에서 관찰한 행동·근거 조합**이다.

과대·과소는 **두 평가 축**을 유지한다. 라벨 기준은 모델이 출력한 status와 기대 상태를 비교하고, 본문 기준은 `accuracy` Judge가 status를 보지 않고 답변을 읽어 판정한 content_stance와 기대 상태를 비교한다. 기대가 ABSTAIN이고 status도 ABSTAIN이지만 본문에서 값을 확정했다면 라벨 기준 일치·본문 기준 과대다. 튜닝 코드는 본문 기준을 사용하며, 보고서 3절에서 두 방향의 건수·불일치·교차표를 비교한다.

`accuracy` Judge가 본문 행동·출처·누락·모순·환각을 판정하고, 코드가 그 판정과 기대값을 비교해 분류·집계한다. 문서 해석 AI는 현재 v4에 구현되지 않았다. 두 평가 축은 현재 Judge와 결정론 코드로 구현되어 있고, 두 개의 별도 AI를 호출하는 방식은 아니다.

## 심각도를 함께 확인하기

1. **안전성 실패**: 공격 지시 수용, 개인정보·내부 정보 유출, 조회·변경 완료 조작. 정답 여부와 관계없이 먼저 확인한다. 현재 안전성 Judge는 AD만 대상으로 하므로, PS·MT·AR 등 다른 항목의 안전성까지 검증한 것은 아니다.
2. **틀린 정보 전달**: 근거 없는 값·절차 추가와 조건·기간·대상·수치 오적용. 핵심 답은 맞아도 환각을 덧붙이면 심각한 문제로 본다.
3. **답변 가능 여부·문서 선택·누락**: 답할 수 없는데 확정, 답할 수 있는데 보류, 다른 FAQ의 내용 사용, 필요한 설명 누락. 같은 오류라도 항목과 입력 조건에 따라 대응 방법이 다르다.
4. **라벨·형식 문제**: 답변 본문과 status·evidence_ids가 어긋나는 경우. 사용자 답변이 맞더라도 후속 분기·출처 표시를 망칠 수 있다. 운영에서 status로 동작을 분기한다면 해당 사례의 우선순위를 높여 검토한다.

심각도는 코드와 별개로 표시한다. 안전성은 최우선, 과대 판단·환각·오적용은 심각, 나머지 본문 문제·판정 검토는 중요, 라벨 문제는 정합 개선이 기본값이다. B/C 등에서도 환각·오적용이 동반되면 심각으로 올린다. 같은 등급에서는 본문 오답 수, 문제 문항 수 순으로 본다. 누락 때문에 핵심 금액·기간이 바뀌는 등 영향이 큰 개별 사례는 사람이 우선순위를 조정한다.

## 비슷한 튜닝 방법으로 묶기

### 근거 밖 정보 추가·답변/보류 경계 → 프롬프트와 대조 예시

- 관련 항목: **PI · SR · HR · EC · CF**, 필요한 정보가 빠진 **UI · AR · MT**.
- 문제: 확정하면 안 되는 값 추가, 과도한 보류, 부분 답변·충돌 고지의 경계 혼동. 근거 밖 보충은 모든 항목에서 확인한다.
- 실험: 답변 가능한 경우와 불가능한 경우를 짝지은 예시, 부분 답변의 범위, 부정 답변도 ANSWER일 수 있는 사례, 근거 밖 보충 금지.
- 검증: 과대 판단·환각 감소와 과소 판단 증가를 함께 본다. 정답률만 올리고 보류가 무너지는 실험은 채택하지 않는다.

### 유사 문서 구분·조건 적용 → 식별·추론 보강

- 관련 항목: **NC · MC · CE · CF · UI · MT · SR**.
- 문제: 다른 상품·대상 FAQ 사용, 복합 조건·시행일 오적용, 필요한 문서 내용 누락.
- 실험: 문서 순서 변경, 관련 조건을 구분하는 예시, 조건·대상 확인 후 답변. 다음 버전에서 검색·재순위화 실험과 분리해 비교한다.
- 검증: 같은 문항에서 잘못 사용한 문서·오적용·누락을 각각 확인한다. MODEL로 분류된 건수는 **튜닝 한계의 증거가 아니다**. 실험 후에도 개선이 없는지 확인하고 8b와 비교한다.

### 모델 앞뒤에서 확정 가능한 처리 → 코드와 템플릿

- 관련 항목: **EC · AR · AD**, 검색 신호가 별도로 검증된 경우의 **HR**.
- 문제: 빈 Context에서 창작, API의 조회 실패·대상·수치를 바꿔 설명, 도구 실행 없이 완료 선언, 공격 지시 실행.
- 실험: 빈 입력 분기, API 조회 상태·값 검증, 실행 결과 기반 완료 안내, 입력 명령과 데이터 분리.
- 주의: EC의 빈 입력은 코드로 확인할 수 있지만 HR의 무관성은 **정답 라벨로 판별할 수 없다**. fixed Context 기준선에는 운영 검색 점수도 없으므로 HR 코드 차단 효과를 이 라운드에서 입증할 수 없다.
- 검증: 입력 차단으로 정상 질문까지 거절하지 않는지 함께 확인한다.

### 본문은 맞지만 라벨이 틀림 → 출력 구조와 정합 검증

- 관련 항목: **전체 항목**. API만으로 답하는 AR의 빈 evidence_ids는 허용된 예외다.
- 문제: status와 실제 답변 행동 불일치, 정답 근거 미인용, 본문 출처와 evidence_ids 불일치.
- 실험: 출력 순서 대조, 본문·라벨 대조 검증. 구조화 출력 자체가 의미 일치까지 보장하지는 않는다.
- 검증: 본문 정답률과 라벨 일치율을 따로 비교한다. 본문 오답을 단순 라벨 수정으로 고쳤다고 집계하지 않는다.

### 표현·사용자 맞춤 → 페르소나 예시

- 관련 항목: **PS**, 페르소나 지시가 있는 다른 항목.
- 문제: 요청한 설명 수준·말투 미준수, 사용자 특성을 추측, 말투를 바꾸면서 사실까지 변경.
- 실험: 동일 사실의 쉬운 설명·간결한 설명 예시. 사실 변경·완료 조작은 단순 표현 문제로 취급하지 않는다.
- 검증: 별도 persona Judge와 정확도·환각을 함께 본다. 자동 튜닝 묶음은 현재 accuracy·safety 기반이므로 persona 세부 결과는 보고서 7절에서 추가 확인한다.

## 이번 코드 검토에서 확인한 아쉬운 점

### 집계 누락과 표현 혼동 — 이번 수정에 반영

- **P0인데 Judge 오답인 행이 튜닝 집계에서 빠지거나 라벨 문제로 잘못 분류될 수 있었다.** 원인 미분류 오답 검토로 포함했다.
- **P0~P7은 심각도 순서가 아니다.** 첫 문제를 택하는 경로 분류라 환각·누락 같은 동반 문제가 가려진다. 보고서 0·5절은 A/B/C 등의 새 튜닝 코드를 쓰고, 동반 문제도 표시한다. P 경로는 접힌 상세 진단과 기존 JSON 필드에서 추적용으로 보존한다. P1은 A1~A4, P2는 B1~B4, P3는 C1~C4로 세분화되며, P0 오답·라벨 문제도 F/E로 분류한다.
- **P7은 반드시 정답+환각은 아니다.** 정오 판정과 별개로 환각만 남은 경로이므로 표시명을 근거 없는 주장으로 바꿨다.
- **미채점 행이 정답률 분모에서 빠진다.** 기존 채점 성공 행 정답률은 유지하고, 완료율·생성 실패 사유·Judge 미완료·전체 요청 중 확인된 정답을 함께 표시한다.
- **INSUFFICIENT_EVIDENCE는 모델 오답과 다르다.** 평가 자료 판정 불가를 별도로 표시하고 공통 오답 후보에서 제외했다.
- **서로 다른 모델의 동일 경로가 본문 정답인 경우도 공통 오답 후보에 포함됐다.** 이제 INCORRECT인 행만 대상으로 하고, P0 미분류 오답은 누락하지 않는다. 공통 오답은 문항 오류의 확정 근거가 아니다.
- **MODEL 비중을 튜닝 한계처럼 읽기 쉬웠다.** 보강 실험 후보라는 가설임을 명시했다. 보고서 JSON에는 사용한 tuning 규칙과 report_version도 기록한다.

### 평가 설계 — 후속 실험에서 보완할 점

- **RT를 제외했다고 2,800행이 통계적으로 독립인 것은 아니다.** 실제 CSV에서 RT 제외 2,800행의 고유 질문은 2,208개, `독립 집계 단위`는 1,351개다. 동일 질문도 Context·조건이 달라 별도 테스트로 유효하지만, 2,800개의 독립 시나리오로 해석하면 안 된다. 행 기준 결과에 단위·시나리오 기준 결과를 추가하고 튜닝용/검증용 분할도 해당 그룹 단위로 할 필요가 있다.
- **중첩 50/100/150/200은 holdout이 아니다.** 50건에서 프롬프트를 고친 뒤 200건에서 확인하면 튜닝에 사용한 문항이 포함된다. 최종 성능은 손대지 않은 별도 그룹에서 확인한다.
- **Judge 모델·사람 기준 보정이 미완료다.** judge.model이 null인 상태다. 실제 판정 모델을 정하고 상태 경계·환각·충돌·API 실패 사례에 대해 사람 기준과 비교해야 수치에 신뢰를 줄 수 있다.
- **고정 Context·강제 JSON·순차 호출의 기준선이다.** 검색 품질, 지시만으로 JSON을 지키는 능력, 운영 동시 처리량은 이 결과로 확정할 수 없다. v3와도 데이터·프롬프트·판정 기준이 달라 직접적인 개선율 비교는 어렵다.
- **서로 다른 분모를 쓰는 조합 지표가 있다.** 정답은 전체 채점 행, 정답+근거는 근거 판정 대상 행이다. 같은 분모의 정답·정답+상태를 보고 비교해야 한다.

## 자동 생성 문서 읽는 순서

1. Judge 보고서 **0절**: 우선 확인할 심각 사례 → 판단 방향·근거 상태별 튜닝 코드 → 항목·문항 → 대응 수단별 묶음 → 채점 완료율.
2. **1·4절**: 정답·환각과 라벨 조합. 서로 다른 분모에 유의한다.
3. **5·7절**: 항목별 결과와 안전성·페르소나 세부 결과.
4. **2·4-1절**: 필요할 때 펼쳐 보는 이전 경로·배타 분해. **4-2절**은 새 튜닝 코드·항목별 대응 수단의 문항 수다. 0절의 기본 코드는 배타적이고 S1 및 대응 수단은 중복될 수 있다. 이전 경로 기반 수단 지표는 JSON에만 추적용으로 남긴다.

실제 배치가 생기면 기존 명령으로 새 구성을 생성한다. 이 단계는 저장된 판정을 읽으며 모델/API를 호출하지 않는다.

