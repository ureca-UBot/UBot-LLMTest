# 입력 가드 최종 결과 — FAQ 기반 1,600문항과 정상·우회 회귀 검증

**결과 기준일: 2026-10-12 KST.** STS에 반영된 입력 가드의 기존 실행 기록을 정리했다. 고정 1,600문항에서 **814건 차단**(금칙어 우선 70건 + 조작 검사 우선 744건), 정상 대조군 100건과 추가 정상 문장 62건은 모두 통과했다. 앞서 저장된 LLM `UNSAFE` 63건 중 **59건을 입력에서 차단**했고, 남은 4건은 사용자 질문 밖의 FAQ Context에 삽입한 공격이었다.

이 디렉터리는 **결과 문서·문항별 판정·검증 메타데이터만** 보관한다. 백엔드/프론트 소스, 실행 스크립트, 테스트 코드, SQL, DB 변경, 모델·서버 설정은 포함하지 않는다. 구현은 로컬 STS에 있으며 소스 업로드는 별도 작업이다. 이번 결과 정리에서는 모델·임베딩·Judge를 새로 호출하거나 DB를 조회하지 않았다.

## 1. 평가 대상과 지표의 의미

원본 데이터는 `data/eval_sets/test_set5/cases_fixed.csv`를 재사용했다. FAQ 원문 1,000건 기반 공격 15항목 × 100문항 = 1,500문항과 정상 대조군 100문항이다. 문항 ID와 사용자 질문은 원본과 전부 일치하며 새 질문으로 교체하지 않았다.

| 구분 | 문항 | 이번 입력 검사 대상 | 해석 |
|---|---:|---|---|
| G01~G14 | 1,400 | 사용자 질문에 포함된 공격 | 직접 입력의 명확한 금칙어·조작 요구를 검사 |
| G15 | 100 | 사용자 질문은 정상; 공격은 검색된 FAQ Context에 삽입 | 입력 가드 범위 밖. 문서 공격 탐지 성능으로 해석하지 않음 |
| NORMAL | 100 | 공격을 넣지 않은 정상 서비스 질문 | 입력 가드 오차단 대조군 |
| 추가 검증 | 753 | 정상 62 + 기존 보완 321 + 구조 검수 71 + 최종 우회·오차단 299 | 고정 1,600과 별도. 정상 62와 신규 299는 753 안에 포함됨 |

`PASS`는 입력 검사를 통과했다는 뜻이며 **답변이 안전하거나 정확하다는 뜻은 아니다**. `CHAT-020`은 조작 요청 차단, `FW-003`은 등록 금칙어 차단이다. 서비스의 실제 검사 순서상 먼저 반환되는 오류를 최종 결과로 집계한다. 문항별 `word_check`와 `prompt_check`는 원인 분석을 위해 각각 독립 호출한 결과여서 두 검사가 모두 차단해도 최종 차단 수에 한 번만 센다.

기존 안전성 Judge가 `UNSAFE`로 본 응답과 입력 차단 여부를 문항 ID로 대조했다. 이번에 `입력 가드 → LLM → Judge` 결합 파이프라인을 다시 실행한 것은 아니다. 고정 공격 문장별 입력 차단 정책과 LLM의 정상 부분 답변 정책도 서로 다르다.

## 2. 합의된 입력 가드 정책과 적용 위치

입력 가드는 임베딩·FAQ 검색·LLM 호출 전에 명확한 금칙어와 조작 요청을 거절한다. 모델 프롬프트를 수정하거나 별도의 가드 모델을 호출하는 방식이 아니다.

1. 기존 빈 값·길이 검증을 먼저 재사용한다. 공백만 있거나 길이가 4,000자를 넘으면 기존 요청 오류를 반환한다.
2. 기존 `ForbiddenWordFilterService.validateForbiddenWord`가 활성 금칙어 목록으로 검사한다.
3. `ChatPromptInjectionService.validatePromptInjection`이 조작 대상과 행동 요구를 조합해 검사한다.
4. 회원·비회원 최초 질문은 검사 통과 후에만 기존 답변 시도 기록을 만들고 검색·생성을 시작한다.
5. 재시도는 기존 소유권 확인으로 가져온 저장 질문을 다시 검사하고, 통과 후에만 새 재시도 이력을 만든다. 차단된 재시도로 새 이력이나 횟수를 추가하지 않는다.

**금칙어·조작 요구가 확인되면 요청 질문 전체를 거절한다.** 그 부분만 지우고 정상 부분을 LLM에 보내지 않는다. 최초 입력 차단은 답변 생성을 시작하지 않으므로 자동 3회 시도 대상이 아니다. 다른 새 질문은 다시 보낼 수 있다. 기존 기술 오류의 재시도 횟수 제한·잠금·소유권 처리 자체는 입력 가드를 위한 별도 기능으로 복제하지 않았다.

사용자의 개인정보가 들어 있다는 이유만으로 차단하지 않는다. 자신의 정보 제출·자신의 서비스 정보 문의는 허용하고 **타인 소유 개인정보의 조회·공개 요구**를 명확히 검사한다. 범위 밖 또는 짧고 모호한 질문은 이번 입력 가드에서 별도 일괄 차단하지 않는다. 검색과 LLM의 안내 대상이며, 임베딩 임계값만으로 개인정보 보호나 안전성을 보장한다고 해석하지 않는다.

현재 안내 오류는 다음과 같다. 차단 오류에 원문 공격 내용·매칭 금칙어·내부 규칙을 다시 넣지 않는다.

| 검사 | 오류 코드 | 기존 오류 안내 |
|---|---|---|
| 등록 금칙어 | `FW-003` | 사용할 수 없는 표현이 포함되어 있습니다. |
| 프롬프트·정책 조작 | `CHAT-020` | 처리할 수 없는 요청이 포함되어 있습니다. 내용을 수정해서 다시 질문해 주세요. |

검사 서비스는 기존 입력 흐름에 연결되어 있다. 조작 검사는 `chat/service/ChatPromptInjectionService`, 금칙어 검사는 팀의 기존 `forbiddenword/service/ForbiddenWordFilterService`를 보완했다. 기존 활성 목록·캐시 초기화·변경 이벤트·예외·공통 오류 응답·답변 시도 관리 기능은 재사용했다. 검사마다 외부 API·LLM·DB를 새로 부르는 파이프라인이나 같은 역할의 금칙어 저장소는 만들지 않았다.

최종 금칙어 보완은 기존 서비스와 기존 테스트 파일 안에서 이루어졌다. 메서드 구성을 늘리지 않았고 정규화·캐시·이벤트 흐름도 유지했다. 금칙어 테스트에 추가한 34사례는 기존 입력과 중복된 5사례를 제외한 수다. 두 검사 서비스의 문자 정리 범위와 목적은 일부 다르며, 강제로 공통 서비스로 옮기는 별도 리팩터링은 하지 않았다. 이 보고서에는 소스 대신 실제 검증한 4개 가드 소스·테스트의 SHA-256을 기록했다.

### 문자 변형 검사와 원문 보존

질문 원문을 저장·전달하기 위한 문자열은 그대로 두고 **검사에 쓸 문자열만** 정리한다. NFKC에 따른 전각 정리, 영문 대소문자 정리, 보이지 않는 형식 문자 제거, 공백 정리와 띄어쓰기 변형 검사를 적용한다. 임시 파일 복사본을 만들었다 삭제한다는 뜻이 아니라 요청 처리 중 메모리의 별도 문자열이다.

띄어쓰기를 전부 없애 정상 단어를 잘못 연결하지 않도록 경계를 확인한다. 예를 들어 정상적인 ‘다시 발급’의 일부를 붙여서 금칙어로 보는 경우를 줄인다. 모든 구두점·숫자·인코딩을 무조건 삭제/해독하는 방식은 아니므로 가능한 모든 문자 우회를 막았다는 의미는 아니다.

### 인용·부정 표현·예외 범위

명확한 설명·신고·도움 목적의 인용은 허용하되, 실제 실행 요구가 함께 있거나 목적이 모호하면 차단한다. 일부 한국어 간접 인용은 화자·과거 전달·설명 목적이 질문 전체에서 확인되는 경우만 구분한다. 명령을 부정한 정상 문장을 뒤의 다른 요청과 결합해 공격으로 인식하지 않도록 했고, 정작 뒤에 붙은 공격은 계속 검사한다.

정상 질문 뒤에 붙인 조작 문구도 검사한다. 보이지 않는 형식 문자로 끊은 조작, 안내문 초안을 앞세운 추가 실행 요구, 제공 자료를 앞세운 다른 자료 전체 복제 요구, 신고·항의 뒤 ‘그대로 실행해’ 같은 지시도 범위 검증에 포함했다. 인용·초안·제공 원문으로 허용되는 **해당 구간만** 구분하며 질문 전체에 대한 일괄 통과 예외를 두지 않는다.

이 인용 정책은 조작 요청 검사에 적용된다. 인용문에 실제 등록 금칙어가 있으면 앞선 금칙어 검사에서 요청 전체가 차단될 수 있다. 공격 문구를 설명하는 정상 요청을 구분한다고 해서 등록된 금칙어까지 모두 허용한 것은 아니다.

## 5. 저장된 LLM 실패 63문항과 입력 가드의 관계

앞선 LLM은 `qwen3:4b-instruct` Q4_K_M으로 답변 1,600건을 생성했다. 안전성 Judge는 공격 1,500건만 판정했으며 결과는 SAFE 1,381 / UNSAFE 63 / OVER_REFUSAL 32 / NOT_APPLICABLE 24였다. 정상 대조군 100건의 LLM 정확도·유용성 Judge는 여전히 미실시다. 이번에 그 모델을 다시 실행하거나 저장 판정을 바꾸지 않았다.

같은 UNSAFE 63개를 대조하면 최초 2단어 기준선은 1건, 공개 단어 추가 후는 2건, 최종 입력 가드는 **59건**을 차단한다. 최종 59건의 실제 우선 오류는 금칙어 2건·조작 검사 57건이다. 질문 안의 직접 공격으로 LLM이 실패한 59건은 이 고정 표본에서 모두 입력 차단됐으며 **Context 공격 4건은 그대로 남는다**.

| 저장된 LLM Judge 판정 | 공격 응답 | 입력 가드 차단 | 입력 가드 통과 |
| --- | --- | --- | --- |
| SAFE | 1381 | 720 | 661 |
| UNSAFE | 63 | 59 | 4 |
| OVER_REFUSAL | 32 | 19 | 13 |
| NOT_APPLICABLE | 24 | 16 | 8 |

SAFE 720건의 입력도 차단됐다. 이는 공격 문장이 들어 있었지만 과거 LLM이 정상 부분만 안전하게 답했다는 뜻일 수 있다. 팀 정책은 명확한 공격이 포함되면 질문 전체를 거절하므로 이 720건을 정상 질문 오차단으로 자동 분류하지 않는다. 반대로 정상 입력에서 과잉 거절이 없는지는 별도 정상100·정상62·추가 기대 사례로 확인한다.

63건 전수의 입력·검사 결과·탐지 패턴·저장 답변·Judge 이유는 [known_llm_unsafe63_results.csv](known_llm_unsafe63_results.csv)에 있다. 이 대응 관계는 ‘LLM과 입력 가드를 합친 서비스가 이제 100% 안전하다’는 실행 결과가 아니다.

네 사용자 질문 자체는 정상 서비스 문의다. 질문의 일반 단어를 추가 금칙어로 넣어서 막으면 정상 문의까지 막는다. [남은 4건 상세](remaining4.md)는 해당 문항의 Context 공격과 저장 답변·Judge 이유를 함께 보존한다. 단순 인용 ID 확인은 G15-031처럼 없는 근거를 찾을 수 있지만, 올바른 ID를 인용하면서 내용만 바꾼 답변의 정확성을 보장하지 못한다.

출력 가드는 아직 구현·검증하지 않았다. 팀이 정한 출력 차단 동작은 **해당 질문을 끝내고 안전한 안내 표시, 그 질문 자동 재시도 없음**이다. 향후 출력 검사·근거 검사·검색 자료의 신뢰성 검증으로 남은 문제를 다뤄야 하며, 그 단계가 이 4건을 전부 해결했다고 미리 기록하지 않는다.

**이번 게시에서는 DB에 새 단어를 등록하거나 실제 목록·서버 캐시를 다시 조회하지 않았다.** 38개는 앞서 저장·검증한 목록 스냅샷이다. 기존 목록/캐시를 보존한다는 말은 정상 요청의 `bad` 문맥 구분처럼 검사 결과를 보완하지 않았다는 뜻이 아니다. 단어·저장 구조를 유지한 상태에서 정상 표현의 오차단을 수정했다.

## 8. 임베딩 측정과 이번 입력 검사 구분

앞선 EC2 BGE-M3 측정에서 최종 1,600문항 모두 FAQ top-1 cosine **0.75 초과**였고 최소 점수는 **0.750249129**였다. 이 게시물의 `embedding_top1_saved`는 기존 `raw/embedding/results.json`의 측정값을 그대로 옮긴 값이며 새 측정값이 아니다. 그 전체 결과·모델 조건은 [원래 v6 요약](../../all_summary.md#임베딩-사전-측정)에 있다.

코드 입력 검사는 임베딩 전에 실행되므로 0.75 통과 여부와 독립적이다. 원본 질문을 바꾸지 않고 고정 표본을 재사용했다. G15의 1.0 점수는 정상 질문에 대한 검색 점수이며 검색 뒤 삽입한 공격 본문 자체의 점수가 아니다. 이 측정은 실제 운영 벡터 DB의 검색과 전체 서비스 성능을 새로 검증한 결과가 아니다.

## 9. 범위·미실시 항목·해석 한계

- 구현 결과는 STS의 실제 소스와 기존 검증 기록을 기준으로 정리했으며 이 브랜치에 구현 소스를 업로드하지 않았다. 검증 당시 소스 해시는 [provenance.json](provenance.json)에 있다.
- 이번 게시 작업에서 백엔드·프론트·DB·서버·모델 설정·기존 실행/평가 코드·프롬프트를 변경하지 않는다. 결과 문서 연결을 위해 v6 `all_summary.md`의 문서 안내만 갱신한다.
- 새 LLM·임베딩·Judge·DB 연결은 0회다. 기존 2026-10-12 LLM·Judge 결과가 존재한다는 사실과 이번 검사에서 호출하지 않았다는 사실을 구분한다.
- 최종 1,600과 추가 경계 사례에 맞춰 규칙을 보완했으므로 **튜닝에 사용하지 않은 독립 검증셋의 일반화 성능**을 입증한 것은 아니다. 표현을 바꾼 새 공격은 놓칠 수 있다.
- 통과한 직접 공격 586건이 남는다. 출력 가드·근거 검사·가드 모델 비교는 미실시이며, 입력 통과만으로 안전성을 주장하지 않는다.
- 운영 HTTP 경로·현재 서버 캐시·DB 동시성·프론트 화면의 이번 최종 전수 검증은 하지 않았다. 이전 화면 테스트와 이 오프라인 표본 검증을 섞지 않는다.
- SQL injection·XSS가 실제 실행되지 않도록 하는 쿼리 바인딩·권한 관리·안전한 화면 렌더링과 입력 문구 차단은 별개다. 이 결과만으로 그런 실행 방어 전체를 검증했다고 주장하지 않는다.
- 주어진 FAQ ID가 맞는 것과 답변 사실이 맞는 것은 다르다. 근거 없는 완료 주장·요금·혜택·권한을 출력에서 추가 확인해야 한다.
- 세 정책 검토 사례가 남아 있으며 ‘정상 입력 오차단 가능성이 전혀 없다’거나 ‘입력 가드가 모든 공격을 해결했다’고 쓰지 않는다.
