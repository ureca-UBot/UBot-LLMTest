# 실험 전체 결론 — 2026-10-03

**현재 고정한 모델·이미지·부하 조건에서 HTTP 완료 8 RPS를 관측한 환경은 L4이며 엔진은 vLLM과 SGLang이다.** 시험한 확대 상한 중 vLLM 64·외부 동시 요청 64와 SGLang 64·외부 동시 요청 64가 후속 검증의 우선 후보다. 이는 반복 검증을 마친 최적 설정이나 운영 동시성 보증이 아니다.

### 측정 기준

`U`는 클라이언트에서 동시에 진행 중인 미완료 요청 수다. 각 워커는 응답이 끝나면 다음 요청을 보낸다. `P`는 Ollama/llama.cpp의 병렬 슬롯, vLLM의 `max-num-seqs`, SGLang의 `max-running-requests` 등 엔진 내부에 설정한 처리 상한이다. 두 수치는 다르다. SGLang 확대 실험에서는 요청 상한과 CUDA graph 최대 batch를 함께 조정했으므로 순수한 요청 상한 한 변수의 효과로 분리하지 않는다.

현재 목표는 30초 측정 창 안에 정상 HTTP 2xx 스트리밍 응답을 끝낸 요청 수를 시간으로 나눈 **HTTP 완료 8 RPS**다. 측정 종료 후 완료한 응답은 RPS에서 제외한다. 지연·의미 품질·실패율의 합격 상한은 적용하지 않았다. 8 RPS 도달은 운영 SLO를 만족하는 동시성이나 지속 도착률을 확정한 결과가 아니다.

### 로컬: 형식과 실행 설정이 성능·응답에 영향을 줬다

RTX 3060 12GB에서 Ollama·llama.cpp는 GGUF Q4_K_M, vLLM·SGLang은 공식 AWQ를 실제 실행했다. vLLM의 원본 Safetensors FP16도 실행했지만 메모리 때문에 eager·작은 내부 상한·context 2048 조건이 필요했다. 이 원본 FP16 대안은 AWQ와 동일 조건의 비교가 아니며 이번 표본에서 AWQ보다 유리하다는 근거를 얻지 못했다.

llama.cpp는 공식 Qwen3 채팅 템플릿과 reasoning/thinking 설정을 맞춰야 정상 JSON 응답을 얻었다. SGLang은 고정 의존성을 보완한 이미지로 기동했다. 같은 AWQ의 로컬 CUDA graph off/on 비교에서는 U4 형식 통과 처리량이 0.85→2.85 RPS로 증가했다. 이 결과는 단일 로컬 관측이며 다른 GPU에 같은 개선 폭을 적용하지 않는다.

초기 로컬 최적화 탐색은 비스트리밍·20초·형식 통과 처리량이고 후속 HTTP 탐색은 스트리밍·30초·HTTP 완료 처리량이다. 두 결과를 같은 지표로 섞지 않는다. 초기 로컬 결과와 클라우드의 모델 파일·소스가 모두 동일 바이트였다고 가정하지 않는다. [초기 로컬 최적화 기록](../local/results/20261002/local_probe/LOCAL_OPTIMIZATION.md), [후속 HTTP 탐색](../local/results/v2/http_8rps_20261002_03/report.json).

### 기본 여섯 설정의 관측값

아래는 각 환경에서 시험한 외부 동시 요청 수 중 최고 HTTP 완료 RPS다. 환경별 최고값의 U가 다르므로 동일 부하점의 인과 비교나 GPU 단독 성능 비교로 읽지 않는다.

| 엔진·내부 상한 | 로컬 RTX 3060 | T4 | L4 |
|---|---:|---:|---:|
| Ollama 4 | 1.20 | 0.73 | 1.40 |
| llama.cpp 4 | 1.53 | 0.97 | 1.80 |
| vLLM 8 | 3.83 | 1.83 | 4.70 |
| vLLM 32 | 3.80 | 1.97 | 9.13 |
| SGLang 8 | 3.70 | 0.70 | 4.17 |
| SGLang 32 | 4.40 | 1.93 | 8.17 |

시험한 기본 설정에서는 로컬과 T4 모두 목표에 미달했고 L4의 vLLM 32·SGLang 32가 목표를 넘었다. T4의 vLLM 32와 SGLang 32 차이는 30초 완료 59건과 58건, 한 건 차이였으므로 안정적인 승자를 확정하지 않는다.

T4→L4에는 GPU뿐 아니라 CPU 4→8 논리 코어, RAM 약 15.4→30.2 GiB 차이가 있다. SGLang의 실제 선택 커널도 T4의 AWQ 경로와 L4의 awq_marlin 경로가 달랐다. L4 기본 다섯 설정과 마지막 vLLM 32는 서버 재시작으로 GPU UUID도 달랐다. 따라서 여섯 기본 설정을 동일 GPU 세션의 엄격한 비교라고 표시하지 않는다. [T4 결과](../t4/reports/T4_SERVING_RESULTS_20261002.md), [L4 기본 결과](../l4/reports/L4_SERVING_RESULTS_20261003.md).

### L4: 상한 확대의 이득은 일정 지점에서 멈췄다

상한 확대 10개와 다양화 질문 4개는 같은 L4 GPU UUID에서 측정했다. 아래 P95는 각 설정의 최고 RPS 단계에서 시작한 성공 요청의 완료 대기 구간을 포함한 지연 참고값이다. GPU 메모리는 워밍업·측정·완료 대기 중 시스템 전체 표본의 최대값이며 기동 전체 구간의 최대값은 아니다.

| 엔진 | 확대 상한별 최고 RPS | 선택 상한·최고값의 U | 선택 단계 P95 | 선택 설정 GPU 최대 |
|---|---|---|---:|---:|
| Ollama | 8: 1.70 / 16: 2.23 / 32: 2.23 | 16 · U32 | 18.14초 | 11.88 GiB |
| llama.cpp | 8: 2.13 / 16: 2.67 / 32: 2.60 | 16 · U16 | 9.80초 | 11.64 GiB |
| vLLM | 64: 9.97 / 128: 8.23 | 64 · U64 | 9.15초 | 17.35 GiB |
| SGLang | 64: 8.77 / 128: 8.43 | 64 · U64 | 10.53초 | 16.37 GiB |

Ollama 상한 32는 16과 최고 처리량이 같았지만 GPU 사용 표본이 11.88→20.71 GiB로 늘고 최고 단계 P95도 18.14→22.30초로 증가했다. vLLM·SGLang 상한 128은 각각 64보다 최고 처리량이 낮고 최고값의 U256에서 P95가 약 32.26·30.67초였다. 더 큰 상한을 설정할 수 있다는 사실이 더 높은 유효 처리량을 보장하지 않았다. [확대 측정 결과](../l4/reports/L4_EXPANSION_RESULTS_20261003.md).

### 질문 다양화: 같은 RPS 목표도 질문 구성에 따라 달라진다

질문 풀은 짧은 조회·복수 근거·긴 문맥·대화 정정·금액 계산·모호성/충돌 6종 각 50개다. 최장 입력은 AWQ 토크나이저 기준 1,352토큰으로 출력 512와 여유 32를 더해 context 4096 안에 들어갔다. 원래 질문과 입력·출력 길이 및 내용이 다르므로 처리량 차이를 엔진의 고정 성능 변화로 단정하지 않는다.

| 선택 확대 상한 | 기존 질문 최고 RPS·U | 다양화 질문 최고 RPS·U |
|---|---|---|
| Ollama 16 | 2.23 · U32 | 1.87 · U16 |
| llama.cpp 16 | 2.67 · U16 | 2.17 · U32 |
| vLLM 64 | 9.97 · U64 | 9.03 · U64 |
| SGLang 64 | 8.77 · U64 | 8.77 · U64 |

vLLM·SGLang은 이 다양화 질문에서도 목표를 넘었다. SGLang의 같은 최고 RPS 관측값 하나로 질문 변화에 영향이 없다고 결론 내리지 않는다. 모든 엔진이 6개 유형을 사용했지만 300개 문항 전체를 모두 사용한 것은 아니다. 서로 다른 실제 사용 문항은 Ollama 112개, llama.cpp 187개, vLLM·SGLang 각 300개였다.

### 전송 실패와 답변 품질은 별도 과제다

llama.cpp의 재사용 소켓 실패는 T4 기본 117/290건, L4 기본 205/466건, L4 확대 세 설정 합계 630/1,447건, 다양화 181/415건이었다. 모두 `socket hang up` 패턴이다. 실제 슬롯 8·16·32와 슬롯당 context 4096을 확인했지만 전송 실패가 섞인 RPS로 계산 성능의 절대 한계를 확정할 수 없다. 전송을 고친 뒤 별도 실험으로 비교해야 한다.

vLLM도 확대 상한 128에서 1건, 다양화 상한 64에서 2건의 재사용 소켓 실패가 있었다. L4 확대·다양화의 Ollama·SGLang에는 HTTP 전송 실패가 없었다. 실패율을 합격 조건에서 제외했더라도 실패 기록을 생략하지 않는다. 스트리밍과 keep-alive는 현재 비교의 공통 조건이며 이 실험만으로 어느 전송 방식이 동시성을 가장 높인다고 확정하지 않는다. 초기 15건 순차 전송 확인은 동시 처리 능력의 근거가 아니다. [실패·실제 슬롯·문항 사용 범위](../l4/reports/L4_EXPANSION_OBSERVATIONS_20261003.json).

초기 로컬 Ollama 일반 JSON 300문항에서 HTTP는 300/300, 형식은 290/300, 근거 ID 존재 검사는 276/300이었다. 같은 60문항에 JSON Schema를 적용하면 형식이 59→60건, 근거가 55→56건으로 바뀌었다. 스키마 강제가 사실성·정확한 인용을 보장하지는 않았다. AWQ의 일부 근거 ID 오류는 원본 FP16에서도 남았으므로 품질 차이를 양자화 한 원인에 귀속하지 않는다. GGUF와 AWQ의 정확한 변환 계보 및 의미 정답률도 미확정이다.

### 초기 v1 결론은 현재 최적화 비교와 구분한다

초기 T4 v1은 여러 모델을 GGUF 위주로 실행했고 P95 5초·실패율 5% 기준을 사용했다. 네이티브 12조합 중 4개만 측정 단계가 완료됐다. vLLM·SGLang의 일부 조합은 GGUF 로더·양자화 shard 호환성·모델 메타데이터 준비에서 실패했다. 이를 엔진의 낮은 계산 성능 또는 처리량 0으로 기록하지 않는다.

Qwen3 4B/8B llama.cpp는 초기 U1에서 5초 기준을 반복 통과했지만 Ollama와 네이티브 엔진의 연결 방식 등이 달랐다. 그 결과로 현재 AWQ 기반 vLLM·SGLang보다 우수하다고 주장하지 않는다. 당시 100명 스파이크도 안정적으로 처리하지 못했다. [초기 v1 결과와 제한](../t4/results/20261001/final_report_20261002.md).

### 메모리 정리와 다음 검증 우선순위

클라우드 기본·확대·다양화의 각 설정 종료 후 실험 컨테이너·worker를 제거하고 같은 GPU에서 메모리 0 MiB·compute PID 없음 상태를 연속 3회 확인한 뒤 다음 설정을 시작했다. 최종 감사도 통과했다. 따라서 모델·KV 캐시가 GPU에 상주한 채 다음 엔진으로 넘어간 결과로 해석하지 않는다. 로컬 Windows의 정리 검증 제한과 클라우드의 실제 0 MiB 검증은 구분한다.

다음 실행을 진행할 때의 우선 후보는 L4 vLLM 64/U64와 SGLang 64/U64다. 내부 상한과 외부 요청 수를 따로 조정하고 같은 문항·길이 분포에서 더 긴 측정과 반복으로 목표 주변의 변동을 확인해야 한다. llama.cpp는 재사용 소켓 문제를 먼저 해결해야 하며 운영 동시성 판정에는 별도로 합의한 TTFT·응답 지연·실패율·답변 품질 기준이 필요하다. 현재 모든 결과는 탐색이며 장기 처리량·SLO 동시성·전역 최적값을 확정하지 않는다.
