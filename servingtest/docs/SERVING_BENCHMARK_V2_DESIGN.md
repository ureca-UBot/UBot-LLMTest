# 서빙 엔진 동시 처리 비교 재설계안

작성일: 2026-10-02. 이 문서는 실행 계획이다. 중단된 로컬 실험과 T4 실험을 재개하지 않는다. 기존 `load_test_v1/` 및 `servingtest/test_v2/`의 결과는 보존한다.

## 1. 질문과 비교 단위

질문은 **같은 LLM 계열의 같은 상위 체크포인트를 각 엔진에 적합한 형태로 배포했을 때, 품질과 응답 지연을 지키며 몇 건을 동시에 처리할 수 있는가**이다. 엔진 이름만 비교하지 않는다. 비교 대상은 `(엔진 버전, 모델 리비전, 가중치 형식·양자화, 채팅 템플릿, 서버 설정)`으로 정의한 **배포 구성**이다.

첫 대상은 `Qwen/Qwen3-4B` 원본 계열로 한정한다. `Qwen3-4B-Thinking-2507`은 다른 체크포인트이므로 같은 표에 넣지 않는다. 후보는 Ollama·llama.cpp의 공식 Qwen3-4B GGUF, vLLM·SGLang의 공식 Qwen3-4B AWQ와 로컬 메모리에 맞는 원본 Safetensors다. 각 엔진에 GGUF를 강제하지 않는다. GGUF Q5/Q6, GPTQ, INT8 등은 **동일 상위 체크포인트와 실제 버전·GPU 호환성을 입증한 뒤** 추가한다. 모델 카드 계보와 로컬 파일 SHA-256, 토크나이저·템플릿을 기록한다.

1차 결과는 **최적 배포 구성 간 비교**다. 형식과 엔진을 함께 바꾼 결과를 `엔진 자체의 순수 성능 차이`라고 부르지 않는다. 원인을 더 좁히고 싶을 때만 같은 GGUF의 Ollama↔llama.cpp, 같은 AWQ의 vLLM↔SGLang을 보조 비교한다. Gemma 3와 Qwen3 8B·14B는 Qwen3 4B 설계가 확정된 다음 각 모델 계열별로 별도 반복한다.

## 2. 공통 요청 계약: 전송 방식은 비교 변수가 아니다

- 같은 300문항 파일·해시·문항 순서, 같은 system/user 메시지, 컨텍스트 4096, 최대 생성 512토큰, temperature 0, Qwen thinking OFF를 사용한다. 입력 잘림, hidden reasoning, 출력 상한 도달을 요청별로 검사한다.
- 모든 엔진에서 **HTTP/1.1 스트리밍 ON**, 동일한 연결 재사용 정책, 동일한 요청 제한시간과 재시도 없음으로 고정한다. 1차 정책은 운영 사용 방식에 맞춰 keep-alive ON이다. T4의 기존 llama.cpp 빌드에는 재사용 소켓 오류 이력이 있으므로 사전 연속 호출 검사를 통과시키거나 버전을 고친 뒤 정식 비교한다. 실패한 엔진만 새 연결로 바꾸어 같은 표에 넣지 않는다.
- 앱이 요구하는 출력 계약은 `status`, `answer`, `evidence_ids` 세 필드의 JSON이다. 엔진마다 이를 만족시키는 구조화 출력 기능을 쓸 수 있으나, 실제 제약 방식과 최종 클라이언트 검증 결과를 기록한다. 서버가 HTTP 200을 보냈다는 것만으로 성공으로 세지 않는다.
- 클라이언트는 동일한 논리적 Chat 요청을 보낸다. Ollama는 `/api/chat`의 NDJSON, llama.cpp·vLLM·SGLang은 `/v1/chat/completions`의 SSE를 어댑터로 읽는다. **스트리밍 여부와 연결 정책은 공통**이지만 바이트 단위 프로토콜이 같다고 주장하지 않는다. `/completion`, `/generate`, 스트리밍 OFF의 속도 대결은 이번 실험에 넣지 않는다.
- 형식이 다른 응답 조각을 토큰으로 세지 않는다. TTFT는 클라이언트가 첫 *내용*을 받은 시각, E2E는 스트림 종료 시각이다. 출력 토큰 수는 엔진 usage·토크나이저로 확인한 값만 사용하고 없으면 `null`로 둔다.

## 3. 동시성의 정의와 판정

`U`는 응답을 기다리는 **클라이언트 요청 수**다. `P`는 Ollama의 병렬 수, llama.cpp 슬롯 수, vLLM의 동시 시퀀스 수, SGLang의 실행 요청 상한처럼 **엔진 내부 한도**다. 두 수치는 같지 않으며, 같은 `P=8`도 엔진 간 동일한 스케줄러를 뜻하지 않는다.

보고할 값은 둘이다.

1. **SLO 동시 요청 한계 `C_SLO`**: 고정된 U의 closed-loop 부하에서 세 회차 모두 품질 게이트를 통과하고, 유효 응답 E2E P95와 실패율 기준을 지킨 최대 U. 측정한 U 단계 중에서만 말한다. `C_SLO=8`은 초당 8건 처리나 내부 시퀀스 8개를 뜻하지 않는다.
2. **지속 가능 도착률 `λ_SLO`**: 응답 완료와 무관하게 도착하는 open-loop 부하에서 같은 기준을 지키고, 측정 후반의 대기열·미완료 요청이 계속 증가하지 않는 최대 req/s. `C_SLO`만으로 지속 가능한 운영 처리량을 확정하지 않는다.

제안하는 **잠정** 지연선은 기존 E2E P95 ≤ 5초다. 실패율은 기존 5%가 운영 판정에는 느슨하므로 ≤ 1%로 제안한다. 실패에는 HTTP·타임아웃·불완전 스트림·JSON 구조 오류·thinking 누출을 포함한다. 실제 서비스 요구를 확인하기 전에는 이 숫자를 확정 운영 SLO라고 쓰지 않는다. TTFT P95, 전체 요청의 E2E P95, 유효 req/s, 출력 tok/s, 출력 길이·절단률을 함께 공개한다. 낮은 P95가 긴 답변을 생략해서 얻어진 것인지 확인한다.

품질 게이트는 300문항의 구조·근거 ID 유효성을 먼저 검사하고, 기준 답안 또는 사람 검토로 의미적 정답의 하한을 정한다. 현재 문항 파일에 정답이 없으므로 **구조 통과만으로 의미적 품질 통과를 선언하지 않는다**. 품질 하한이 정해지기 전의 성능 순위는 `성능 후보`로만 표시한다.

## 4. 실험 순서

| 단계 | 수행 내용 | 산출물과 다음 단계 조건 |
|---|---|
| A. 재현성 검사 | 같은 원본 계보, GGUF/AWQ/Safetensors 리비전, 토크나이저·채팅 템플릿, GPU 적재·오프로딩, thinking OFF, 구조화 출력, keep-alive 연속 요청을 확인 | 설정·실제 요청 본문·파일 지문·로그. 하나라도 불일치하면 부하 측정 제외 |
| B. 후보 탐색 | 로컬 GPU에서 엔진별 형식 후보를 기동한 뒤 **한 번에 한 설정만** 바꾼다. 예: GGUF 정밀도/슬롯/KV, vLLM AWQ·원본/graph·배치 예산, SGLang AWQ·원본/graph·scheduler. U=1/4/8/12/16을 각 60초 1회로 훑는다 | 엔진별 1~2개 후보. 이 짧은 결과로 최종 순위를 정하지 않음 |
| C. 품질 검증 | 후보별 동일 300문항. 구조, 근거, 절단, 답변 원문과 의미적 오류를 확인 | 품질 하한을 넘은 구성만 정식 부하로 이동 |
| D. 정식 T4 | 로컬에서 좁힌 후보만 단일 T4에서 **한 번에 한 엔진·모델** 기동. U=1/2/4/8/12/16/24/32, 단계당 180초·3회, 각 단계 성공 응답 100건 미만이면 표본 부족으로 표시하고 해당 단계를 연장하거나 보류 | 회차별 `C_SLO`, valid req/s, 토큰 처리량, 지연, 오류, 자원·queue/KV 로그 |
| E. 지속성 확인 | D에서 얻은 처리량의 0.7/0.9/1.1배 도착률을 단계당 최소 5분 유지, 종료 뒤 drain 시간 측정 | `λ_SLO`, 큐 증가·타임아웃·GPU 안정성 판정 |

부하 단계는 미리 정한 U까지 진행한다. **사용자를 두 배로 늘렸는데 처리량 증가가 10% 미만이라는 이유로 다음 U를 자동 생략하지 않는다.** 배칭 때문에 처리량 곡선이 단조 증가한다고 가정할 수 없다. 엔진 OOM·프로세스 종료·GPU 오프로딩·반복적인 타임아웃처럼 측정 자체가 위험하거나 무의미해진 경우에만 안전 중단하고, 뒤 단계는 `미측정(중단 사유)`로 남긴다. 단계 시간 상한에 걸리거나 P95를 계산하기에 표본이 부족하면 성공/실패로 억지 판정하지 않는다.

매 회차의 초기 로딩·프롬프트 캐시 워밍업을 본 측정에서 제외하고, 실제 요청 순서와 접두부 캐시 적중률을 기록한다. 후보·회차 순서는 고정 순서 편향을 피하도록 교차한다. 한 엔진이 끝나면 소유 컨테이너와 worker를 종료·제거하고 포트 해제, GPU 프로세스 없음, 전체 실험 시작 시 고정한 VRAM 기준선 복귀를 연속 3회 확인한 뒤 다음 엔진을 시작한다. 기본 VRAM 허용 오차는 0MiB이며 미확인·정리 실패는 해당 회차 합격과 다음 엔진 실행을 차단한다. 실제 측정은 worker 전체 종료를 확인할 수 있는 소유 Docker 컨테이너에 한정한다. RTX 3060 결과를 T4 수치로 환산하지 않는다.

## 5. 선택 규칙과 결과표

엔진별로 품질·안정성·잠정 SLO를 통과하는 구성 중 `C_SLO`가 가장 큰 것을 고른다. 같으면 그 U의 유효 req/s, 다음으로 출력 tok/s와 VRAM 여유를 본다. 어느 구성도 통과하지 못하면 `합격 없음`으로 기록하고 최대 처리량을 승자로 부르지 않는다.

최종 행에는 `엔진/버전 | 상위 체크포인트·리비전 | 형식·양자화 | P·컨텍스트·KV·graph | C_SLO | λ_SLO | U별 유효 req/s·출력 tok/s | TTFT/E2E P95 | 실패·형식·의미 품질 | peak VRAM | 상태`를 둔다. 4개 엔진을 **같은 U에서도** 비교하고, 최고 수치만 추려 보여 주지 않는다. 실행되지 않은 조합은 `미실행`, 로드 실패는 `호환성 실패`, 표본 부족은 `판정 보류`로 구분한다.

## 6. 기존 코드에서 바꿔야 할 부분

현재 `servingtest/test_v2`는 참고 구현이다. 새 실행기를 만들 때 다음을 반영하고 v1 원본은 수정하지 않는다.

1. `stream_client.js`는 Ollama 연결 재사용이 고정이고 `openai_stream_client.js`는 기본이 새 연결이다. 공통 `transport` 설정을 두 어댑터에 주입하고 실제 소켓 재사용 여부까지 기록한다.
2. `load_config.js`와 `run_load_test.js`의 `minGain`·`parallelMinGain`에 의한 조기 중단을 정식 탐색에서 제거한다. 실패율·P95는 **결과 판정**으로 쓰고, 중단은 별도 안전 규칙으로 제한한다. 튜닝 모드에서만 이 두 값이 꺼지는 현재 구조도 통일한다.
3. `stats.js`의 `ok`는 스트림 완료를 뜻한다. 구조 검증과 최종 품질 판정을 별도 필드로 저장하고 `valid req/s`의 분자를 명시한다. 종료 경계에 걸친 요청, 타임아웃과 drain을 분리 집계한다.
4. 모델 태그 대신 원본 체크포인트 계보·리비전·파일 지문을 실행 ID에 포함한다. 지금처럼 이름이 같은 다른 체크포인트가 한 비교표에 들어오면 사전 검사에서 막는다.
5. 스모크 검증에는 두 스트림 어댑터의 동일한 완료·오류·타임아웃 처리, keep-alive 연속 호출, JSON 구조 검사, 조기 중단 규칙을 포함한다.

참고 코드: `D:/finalproject/UBot-LLMTest/servingtest/test_v2/scripts/`. 참고 측정: `results/20261002/local_probe/LOCAL_OPTIMIZATION.md`. 이전 로컬 측정은 비스트리밍이고 초기 GGUF와 AWQ의 상위 체크포인트가 다르므로 이 설계의 정식 엔진 순위에 합치지 않는다.
# 구현 상태 (2026-10-02)

별도 `load_test_v2`에 공통 스트리밍 어댑터, 계보/품질 게이트, 고정 구간 closed-loop, Poisson open-loop, 원문/메트릭 기록과 소유 리소스 정리를 구현했다. 검증 범위는 **구현 및 로컬 HTTP 모의 검증**이다. 기존 v1과 외부 servingtest 코드는 수정하지 않았으며 실제 엔진·모델 등록·T4 측정은 진행하지 않는다. 실제 엔진별 probe와 검토된 모델 계보·의미 품질 증거를 채우기 전에는 실측 후보를 활성화하지 않는다. 사용법과 미확정 기준은 `load_test_v2/README.md`를 따른다.
