# AWS T4 기반 LLM 서빙 엔진 동시처리 비교 설계안

문서 기준일: 2026-10-01

AWS EC2 g4dn.xlarge의 Tesla T4 16GB 한 장에서 Ollama, llama.cpp, vLLM, SGLang을 비교한다. 기존 부하 테스트의 성능 판정 기준을 유지하고, 엔진 비교 설계의 모든 성능·자원·안정성 측정 지표와 시나리오를 포함한다. 출력은 모든 비교 요청에서 최대 512토큰으로 제한한다. 문항은 부하 입력으로만 사용하며, 평가 Excel·정답 데이터 연결과 응답 품질 채점은 이번 측정 범위에서 제외한다.

## 1. 환경과 비교 대상

| 항목 | 조건 |
|---|---|
| 인스턴스 | AWS EC2 g4dn.xlarge |
| GPU | NVIDIA Tesla T4 16GB, 1장 |
| 모델 | gemma3:4b, qwen3:4b, qwen3:8b, qwen3:14b |
| 엔진 | Ollama, llama.cpp, vLLM, SGLang |
| 비교 조합 | 4개 모델 × 4개 엔진 = 16개 |
| 동시 기동 | 서빙 엔진 1개·모델 1개만 허용. 조합은 순차 실행 |
| 공통 환경 | 동일 인스턴스, OS 이미지, 드라이버, 스토리지, 네트워크, 테스트 클라이언트 |

각 엔진에서 실제 배포 가능한 구성을 비교한다. 모델 포맷과 양자화가 다르면 결과는 해당 전체 구성의 성능 차이로 해석한다. 모델 이름만 같은 것을 동일한 체크포인트·양자화라고 간주하지 않는다.

Ollama 태그 외 엔진에서는 대응하는 모델 소스, 체크포인트와 chat template을 명시한다. GGUF·FP16·AWQ·GPTQ 등은 후보 예시이며, 해당 T4와 엔진 버전에서 로딩과 실행이 확인된 구성만 비교한다. FP8을 기본 전제로 두지 않는다. 실행할 수 없는 조합도 원인과 설정을 기록한다.

GPU 사용률이나 전력 상한 도달만으로 성능 합격·실패를 판단하지 않는다. 실제 GPU의 전력 상한을 조회해 기록한다.

## 2. 공통 요청 조건

| 항목 | 값 |
|---|---|
| 컨텍스트 정책 | 4096토큰 |
| 최대 출력 | 512토큰 |
| 스트리밍 | ON |
| Temperature | 0 |
| Ollama 출력 형식 | JSON |
| Qwen 추론 | OFF. 엔진별 적용 방법과 실제 프롬프트를 기록 |
| Gemma 추론 옵션 | 기존 Ollama 요청에서는 think 미전송 |
| 요청 타임아웃 | 30초 |
| 부하 문항 | 총 300건. 15개 항목별 20건씩 표본 추출 |
| 질문 순서 | 동일 표본, seed 20261001. 항목을 섞어 한 묶음에 항목별 1건씩 배치 |
| 반복 횟수 | 정식 비교는 총 3회 |

Ollama 측정 요청은 `options.num_predict=512`를 보낸다. 다른 엔진은 대응하는 출력 상한을 적용하고 실제 요청을 기록한다. EOS가 먼저 나오면 512토큰보다 적게 생성한다. 모델 사전 로딩용 요청의 `num_predict=1`은 측정 요청과 구분한다.

출력 상한 도달 여부, 종료 사유, 출력 토큰 수와 전체 답변을 저장한다. 현재 Ollama 부하 실행기의 요청 성공은 HTTP·스트림 완료 기준이며, 답변 내용·정답 일치·JSON 형식 정확도는 채점하지 않는다. 출력 상한에 도달했다는 이유만으로 요청 실패로 처리하지 않는다.

부하 문항은 기존 CSV나 별도로 고정한 프롬프트로 준비할 수 있다. 평가 Excel, 정답, 난이도와 채점 기준을 연결할 필요는 없다. 모든 엔진·모델에 같은 문항·시스템 지시·순서를 적용하며, 문항에 대화 이력이나 참고 자료가 있으면 같은 내용을 보낸다. 엔진별 chat template의 역할 의미와 출력 형식 조건을 맞춘다.

입력 길이와 출력 예약량이 컨텍스트 정책에 맞는지 확인한다. 입력을 잘랐거나 넘친 요청은 원인과 처리 방법을 기록하고, 정상 입력과 섞어 비교하지 않는다.

## 3. 성능 판정 기준

기존 `load_config.js`의 SLO를 유지한다.

| 항목 | 기준 |
|---|---|
| 성능 합격 | 성공 요청의 E2E P95 ≤ 5초이고 전체 측정 요청의 실패율 ≤ 5% |
| 더 엄격한 참고선 | 성공 요청의 E2E P95 ≤ 3초 |
| 최적 설정 선택 | 위 기준을 만족한 최대 동시 사용자 수가 가장 큰 설정 |
| 최대 사용자 수가 같을 때 | 해당 사용자 단계의 req/s가 높은 설정 |
| 합격 설정이 없을 때 | 최대 req/s로 비교 후보를 표시하되, SLO 미충족이라고 명시 |

TTFT, TPOT/ITL, 사용자당 tok/s, VRAM과 전력은 모두 측정·보고한다. 이 지표에 새로운 숫자 기준을 붙여 기존 성능 판정을 바꾸지 않는다. 성공 요청 기준 P95와 실패까지 포함한 체감 P95를 함께 보고한다. 응답 품질은 판정·측정 항목에서 제외한다.

동접 10 결과는 공통 비교점이다. 동접 16은 여유 확인점이며, 합격 판정 자체는 각 사용자 단계에 기존 SLO를 적용한다. 동접 10이 미달이어도 더 낮은 동접의 합격 범위를 보고한다.

OOM, 서버 종료, 스트리밍 중단, 요청 손실, 대기열 증가도 기록한다. 요청 실패는 실패율에 반영하고, 로딩 실패처럼 정상 측정이 불가능한 조합은 측정 불가로 분리한다. CPU 오프로딩이 발생한 구성도 상태를 기록하고 기존 GPU 적재 기준에 따라 별도 취급한다.

## 4. 단계 중단 조건

기존 조건을 유지한다.

- E2E P95가 10초를 초과한다.
- 실패율이 5%를 초과한다.
- 사용자를 두 배로 늘려도 req/s 증가가 10% 미만이다.
- GPU에 모델을 전부 적재하지 못하거나 모델 로딩에 실패한다.
- 최대 사용자 64명에 도달한다.
- Ollama 병렬 처리 설정을 두 배로 늘려도 최대 req/s 증가가 10% 미만이면 더 높은 설정을 생략한다.

사용자 5·10명은 별도 공통 비교점이다. 처리량 정체 판단은 기존 두 배 간격 단계끼리 계산하고, 4→5 또는 8→10에 같은 증가율 조건을 그대로 적용하지 않는다.

중단 조건은 위험하거나 더 높은 단계의 측정 여부를 결정한다. 합격 기준 5초와 중단 기준 10초를 구분한다. 특정 단계가 미달이었다는 이유로 다른 시나리오 전체를 완료 처리하지 않는다. 안전하게 진행할 수 없는 경우는 생략 사유를 남긴다.

## 5. 모든 측정 시나리오

| 시나리오 | 부하 | 목적 |
|---|---|---|
| 단일 사용자 | 사용자 1명 | 엔진·모델별 기준선 |
| 단계적 증가 | 기존 1/2/4/8/16/32/64명과 공통 비교점 5·10명 | 동시성 증가에 따른 처리량과 지연 변화 |
| Burst | 사용자 10명 동시 요청 | 목표 동접의 순간 유입 |
| 기존 Spike | 사용자 100명 동시 요청 | 과부하 시 대기·타임아웃·실패 |
| 도착률 | 최적 설정 최대 req/s의 0.25/0.5/0.75/1.0/1.25배 | 응답 완료와 독립적인 지속 유입 |
| Steady State | 사용자 10명, 응답 완료 후 think time | 장시간 지연·대기열·메모리 변화 |
| Shared Prefix | 긴 공통 시스템·서비스 정책과 개별 질문 | prefix cache 효과 |
| Long Prompt | 입력 2K~3K토큰, 최대 출력 512토큰, 사용자 10명 | prefill 부하와 KV cache 압박 |
| 반복 측정 | 동일 설정·문항 순서로 총 3회 | 측정 편차 |

기존 단계적 증가와 Steady State는 별도 시나리오다. 기존 closed-loop는 응답 후 바로 다음 요청을 보낸다. Steady State는 think time을 두며, 초기 실험값은 1초·워밍업 제외 최소 5분으로 정한다. 이 값은 서비스 실측값이 아닌 시험 기본값으로 기록한다.

단계적 증가의 기본 측정은 워밍업 후 최소 60초·40건, 단계 최대 240초다. 이미 보낸 요청은 타임아웃 또는 완료까지 기다린다. 모델 로딩 직후 워밍업과 사용자별 첫 요청 워밍업을 구분해 측정에서 제외한다.

모든 조합에서 모델 로딩 시간, 모델 워밍업 시간, 안정화 대기, 사용자별 워밍업 시간과 본 측정 구간을 각각 기록한다. 워밍업에는 시작·종료 시각, 소요 시간, 요청 수, 성공·실패 수와 오류 사유를 남긴다. 모델 워밍업이 성공해야 부하를 시작하고, 단계적 증가에서는 모든 사용자의 첫 요청이 성공해야 본 측정 구간을 연다. 워밍업 중 실패하거나 제한 시간 안에 완료되지 않으면 본 측정을 시작하지 않고 워밍업 실패·미완료로 기록한다.

도착률 테스트는 포아송 도착을 사용하고 배수별 60초 측정한다. 기존 실패율 50% 초과 시 더 높은 배수 생략, 최대 in-flight 256건 조건을 유지한다. 클라이언트가 보내지 못한 요청 수는 서버 요청 실패와 별도 집계한다.

Shared Prefix는 각 엔진의 캐시 설정과 준비 절차를 기록한다. 공통 입력 길이·내용과 사용자별 질문을 맞추고, 일반 부하 결과와 별도 표로 보고한다. Long Prompt는 실제 입력 토큰 수를 확인한다.

총 16개 조합과 위 시나리오를 결과표에 모두 둔다. 완료, 측정 불가, 안전 조건으로 생략, 미실행을 구분한다. 기존 210분 예산으로 전체 확장 실험을 끝냈다고 가정하지 않는다. 시간이 부족하면 같은 설정을 유지해 실행 세션을 나누고 미실행 항목을 남긴다.

| 범주 | 수집·보고 항목 |
|---|---|
| 첫 응답 | TTFT p50/p95/p99 |
| 응답 완료 | 성공 요청 E2E p50/p95/p99/최대, 실패 포함 체감 P95 |
| 생성 지연 | TPOT, ITL p50/p95/최대, 요청별 평균 조각 간격 |
| 처리량 | req/s, aggregate output tok/s |
| 사용자 속도 | 요청별 출력 토큰/E2E, TTFT 이후 생성 속도, 엔진 decode 속도 |
| 성공·실패 | 성공률, 실패율, 오류 유형, 타임아웃, 요청 손실, 클라이언트 drop |
| 대기열 | 실제 queue time, 대기 시간 추정치, running/queued/in-flight 수 |
| 메모리 | 로딩 직후 VRAM, peak VRAM, 모델·KV 적재 크기, CPU 오프로딩, 시스템 RAM |
| GPU | 사용률, 메모리 사용률, 전력, 전력 상한, SM 클럭, 온도 |
| CPU | 전체 CPU, 엔진 CPU, 부하 발생기 CPU |
| 입력·출력 | 입력·출력 토큰 수, 입력 길이, 출력 상한 도달 비율, 종료 사유, 답변 내용 |
| 준비 시간 | 모델 로딩 시간, 모델 워밍업 시간·요청 수·실패 수, 안정화 대기, 사용자별 워밍업 시간, 본 측정 구간 |
| 안정성 | OOM, 서버 종료, 스트리밍 중단, 지연·대기열·메모리 증가 |
| 재현성 | 회차별 값, 평균·표준편차, 실제 실행 설정 |

지표 정의는 엔진 간에 맞춘다.

- 기존 Ollama의 ITL은 응답 조각 사이 간격이다. 한 조각을 항상 한 토큰으로 간주하지 않는다. 토큰 단위 ITL을 얻지 못하면 조각 간격으로 명시한다.
- TPOT는 첫 토큰 이후 마지막 토큰까지 걸린 시간을 출력 토큰 수에서 1을 뺀 값으로 나눈다. 단일 토큰 출력이나 필요한 시각이 없는 요청은 해당 값을 비워 둔다.
- 사용자당 출력 토큰/E2E는 대기·입력 처리 시간을 포함한다. 엔진이 보고하는 decode tok/s와 섞지 않는다.
- 기존 단계적 증가 처리량은 측정 구간에 완료된 성공 요청과 출력 토큰을 구간 길이로 나눈다. 도착률·스파이크는 전송 기간과 요청 완료까지의 시간을 함께 기록한다.
- 실제 queue time은 엔진의 측정 가능한 값으로 수집한다. 지원되지 않으면 미지원으로 표시하며 0으로 대체하지 않는다.
- 기존 대기 추정값인 `E2E - prompt_eval - eval`은 네트워크·로딩 등 오버헤드도 포함할 수 있다. 실제 queue time과 별도 열에 둔다.
- warm-up, 안전 조건에 의한 중단, 최소 요청 수 미충족과 계측 미지원도 결과에 표시한다.

| SGLang | KV 메모리 설정, running request 제한, chunked prefill, prefix/Radix cache, scheduler, 양자화 |

파라미터 이름과 지원 여부는 실제 설치 버전에서 확인한다. 모든 비교에서 엔진 버전, 모델 소스·리비전, weight format·quantization·크기, CUDA·드라이버, 실행 인자, 환경변수, chat template, 요청 본문과 로딩 직후 메모리를 남긴다.

Ollama-current와 Ollama-tuned를 구분할 수 있다. 두 경우 모두 공통 요청 조건인 context 4096·출력 상한 512를 적용하며 서버 설정 차이를 기록한다. 기존 정식 실행기는 Flash Attention OFF·KV f16 등 고정 설정을 사용한다.

## 8. 부하 문항

문항은 모델에 요청을 보내기 위한 입력이다. 3,000건 전체를 실행하지 않고 항목별 비율을 유지한 300건만 사용한다. 제공된 데이터의 15개 항목은 각각 200건이므로 항목마다 20건씩 추출하면 전체 비율을 그대로 유지한다. 표본 크기 300건은 이번 시험 기본값이다. 표본을 더 줄일 때도 항목별 배분 비율을 맞춘다. 별도 정답표·채점기·정확도·페르소나 평가도 만들지 않는다.

항목마다 원본의 난이도 비율인 Easy/Medium/Hard 30%/40%/30%를 유지해 6/8/6건을 seed 20261001로 추출했다. 난이도는 표본 구성에만 사용하며 모델 입력이나 품질 판정에는 쓰지 않는다. 반복 항목 RT는 고유 20문항을 각 1회 포함한다. 실제 요청 내용인 질문·참고 자료·대화 이력·사용자/API 정보·페르소나 지시만 실행용 JSONL에 남기고 정답·채점 열은 제외했다.

비교를 재현할 수 있도록 실제 문항 파일·내용, seed, 요청 순서와 입력 길이를 기록한다. 동일한 문항 풀을 모든 조합에 사용하고, Long Prompt와 Shared Prefix의 입력 조건을 별도로 고정한다. 정답률을 재지 않아도 입력 길이와 생성 길이는 성능에 영향을 주므로 실제 입력·출력 토큰 수와 분포를 함께 보고한다.

실행용 표본은 `benchmark_prompts.jsonl`, 출처·추출 비율·seed·해시는 `benchmark_prompt_sample.json`에 저장한다. ZIP의 `data/`에도 두 파일을 포함했고 현재 Ollama 실행기의 기본 입력으로 연결했다. `LOADTEST_PROMPTS` 환경변수로 다른 JSONL이나 기존 CSV를 지정할 수 있다. 문항 파일 해시가 바뀌면 같은 실행 기록에 이어 붙이지 않는다. 실제 임베딩 검색·리랭커·Spring·SSE를 포함한 서비스 전체 평가는 이번 범위에 포함하지 않는다.

300건은 고유 문항 풀의 크기다. 각 단계는 이 표본을 순환하며 기존 워밍업 후 최소 60초·40건 조건을 충족할 때까지 요청한다. 단계별 실제 요청·답변 수는 별도로 기록한다. 전체 항목을 한 번씩 포함하는 15건 묶음으로 요청 순서를 구성해 짧은 측정에서도 항목 비율이 크게 치우치지 않게 한다.

## 9. 결과물과 실행 순서

한 T4에 여러 서빙 엔진이나 비교 모델을 동시에 띄우지 않는다. 각 `(엔진, 모델, 실행 설정)` 조합의 측정을 마치고 GPU 자원을 해제한 뒤 다음 조합을 시작한다. 이 직렬 실행 제약과 한 서버에 보내는 동시 사용자 요청은 별개다. 사용자 10·100명의 요청은 현재 기동한 서버 하나에 보낸다.

각 조합은 다음 순서로 진행한다.

1. 이전 서버와 모델 runner·worker 프로세스가 종료됐는지 확인한다.
2. GPU compute 프로세스와 VRAM 사용 상태를 확인하고, 잔여 엔진이 있으면 다음 기동을 보류한다.
3. 대상 엔진 하나와 모델 하나를 기동하고 설정·PID·로그·로딩 시간을 기록한다.
4. readiness와 단일 요청을 확인한 뒤 워밍업한다.
5. 현재 조합의 모든 시나리오와 반복 측정을 수행한다. 설정 변경이 필요한 경우 같은 조합 안에서도 종료→재기동→워밍업 순서를 따른다.
6. 원본 기록을 저장하고 진행 중 요청의 완료 또는 취소를 확인한다.
7. 서버와 runner·worker를 정상 종료한다. 제한 시간 내 종료하지 못하면 관리 중인 프로세스만 정리하고 결과를 기록한다.
8. 포트·GPU compute 프로세스·VRAM 해제를 확인한 다음 다음 조합을 기동한다. 정리가 실패하면 전체 전환을 중단하고 원인을 남긴다.

예를 들어 Ollama/gemma3:4b 측정→종료→해제 확인, Ollama/qwen3:4b 측정→종료→해제 확인을 진행하고, 나머지 Ollama 모델을 마친 뒤 llama.cpp·vLLM·SGLang 조합도 같은 절차로 측정한다. Ollama를 기준선 서버라는 이유로 다른 엔진 측정 중 GPU에 남겨 두지 않는다.

전체 비교 중에는 이전 엔진의 자동 재시작을 막는다. 평소 서비스 설정 원복과 재기동은 모든 비교가 끝난 뒤 별도로 수행한다. 재개 시 완료한 조합은 건너뛰되 이전 실행의 잔여 프로세스부터 확인한다.

원본 요청·단계·시스템 계측·실행 설정은 JSONL/JSON으로 보존한다. CSV 비교표, Markdown 상세 결과와 동시성 그래프를 만든다.

나온 답변은 모든 요청별 `requests.jsonl`의 `content`에 원문으로 저장한다. 엔진·모델·문항 ID·항목·기록 시각·시나리오·회차·워밍업 여부·응답 시간·출력 토큰 수·종료 사유·오류를 함께 남긴다. 워밍업 답변도 보존하되 본 측정 집계에서 제외한다. 실패·타임아웃 때도 수신한 답변 조각까지 남기고 실패 사유를 표시한다. 정답 채점은 수행하지 않는다. 질문은 입력 JSONL의 문항 ID로 찾을 수 있으며 실제 입력 파일의 경로·해시·항목별 건수는 실행 메타데이터에 기록한다.

| Model | Engine | Weight/Quant | Scenario | Users | E2E P95 | Fail rate | SLO | TTFT P95 | TPOT | User tok/s | Agg tok/s | Peak VRAM | 측정 상태 |
|---|---|---|---|---:|---:|---:|---|---:|---:|---:|---:|---:|---|

최종 보고서는 기존 SLO를 만족한 최대 사용자 수, 해당 단계의 req/s, 동접 10·16 결과, 메모리·캐시·운영 조건을 함께 제시한다. 엔진 추천과 실제 실행 설정, queue 제한·fallback 방안은 측정 결과를 얻은 뒤 작성한다.

## 10. 현재 구현 상태

| 항목 | 상태 |
|---|---|
| 기존 Ollama 부하 실행기 | ZIP에 포함. 실행용 300건 JSONL 표본을 기본 입력으로 연결 |
| 출력 상한 512 | full·quick 설정과 ZIP의 실제 스트리밍 요청에 반영 |
| 기존 SLO와 중단 조건 | 유지 |
| 워밍업 계측 | 모델 로딩·모델 워밍업·사용자 워밍업을 분리 기록. 성공한 워밍업 뒤에만 본 측정 시작 |
| 답변 원문 기록 | 요청별 content 저장. 워밍업·실패 요청도 구분하며 수신한 부분 답변 보존 |
| Ollama 모델 전환 | 모델별 A→B→C 완료 후 서버 종료·GPU compute 프로세스 해제 확인. none 모드는 unload 후 수동 서버 종료 |
| 기존 기록 분리 | run_id 조건에 out512·sample300 추가. 문항 SHA-256으로 재개 입력 일치 확인 |
| 다른 세 엔진의 요청·서버 제어 | 구현. SSE 어댑터·엔진별 CLI·readiness·프로세스 그룹 정리·GPU/포트 해제 확인 |
| 세 엔진 × 네 모델 순차 실행 | run_engines.js에 구현. EC2 모델 경로·버전·양자화 설정 후 활성화. 미설정·실패 상태 분리 |
| 사용자 5·10명, Burst 10명 | 추가 구현 필요. 현재 실행기는 기존 사용자 단계·Spike를 사용 |
| Steady State, Shared Prefix, Long Prompt | 추가 구현 필요 |
| 전체 지표 공통 집계 | E2E·TTFT·조각 간격·TPOT·user tok/s·전력·RAM·엔진 CPU와 native metrics 원문 수집. 요청별 queue time 등 미지원 지표의 공통 집계 추가 필요 |
| Excel·정답 데이터 연결과 품질 채점 | 이번 측정 범위에서 제외. 구현 불필요 |
| 실제 T4 측정 | 미실행 |

이 문서는 전체 측정 범위를 확정한 설계이며, 구현되지 않은 항목을 측정 완료로 취급하지 않는다. Ollama는 `run_all.sh`, 다른 세 엔진은 `run_engines.js`를 사용한다. 전체 엔진 비교 중 Ollama의 자동 원복·재기동을 막고 모든 측정·자원 해제를 마친 뒤 원복한다. 새 엔진 실행 설정과 EC2 절차는 [ENGINES.md](ENGINES.md)에 설명한다.

## 11. 변경 기록

2026-10-01: 전달받은 L4 설계의 환경을 기존 T4 16GB로 변경했다. 출력 상한 512토큰을 기존 Ollama 코드와 배포 ZIP에 적용했다. 성능 판정은 기존 E2E P95 5초·실패율 5%로 유지하고, 성능·자원·안정성 지표와 모든 부하 시나리오, 기존 도착률·반복 측정을 비교 범위에 포함했다. 한 번에 한 엔진·모델만 기동하며 측정→종료→GPU 해제 확인→다음 조합으로 진행하도록 순차 실행 조건을 추가했다. 모델 로딩·워밍업을 분리해 기록하고 워밍업 성공 후 본 측정을 시작한다. 문항은 부하 입력으로만 사용하며 평가 Excel·정답 연결과 품질 채점은 제외했다.

추가 변경: 문항 3,000건 전체 대신 15개 항목별 20건, 총 300건의 표본을 만들었다. 항목 비율과 항목 내 난이도 비율을 유지하고 RT 중복 실행 회차는 제거했다. 실행용 JSONL에는 모델 입력만 포함한다. 이 표본을 ZIP의 기본 입력으로 연결하고 기존 결과와 구분했다.

엔진 구현: llama.cpp·vLLM·SGLang의 OpenAI 호환 SSE 요청과 엔진별 서버 기동·모델 readiness·순차 종료를 기존 A/B/C 측정기에 연결했다. 설정 해시·엔진별 보고서·부분 답변 보존·미지원 토큰 계측 null 처리를 추가했다. 예시 설정은 실제 EC2 버전·가중치 정보를 채우기 전에는 비활성화 상태다. 로컬에서는 모의 검증·dry-run만 수행하며 실제 T4 호환성 검증은 미실행이다.
