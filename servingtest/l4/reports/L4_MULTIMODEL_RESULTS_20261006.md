# L4 모델 확장 측정 결과 — EXAONE 3.5 7.8B·Gemma3 4B·Qwen3-8B·Qwen3-14B

측정일: 2026-10-06. NVIDIA L4 한 장에서 Qwen3-4B 기본 측정과 같은 부하 조건으로 네 모델을 추가로 실행했다. **공식 배포 가중치로 HTTP 완료 8 RPS를 넘은 것은 기존 Qwen3-4B뿐이다.** Qwen3-8B와 EXAONE 3.5 7.8B는 6.5 RPS 근처에서 멈췄고 Qwen3-14B는 3.3 RPS였다. Gemma3 4B 커뮤니티 AWQ 형식은 20 RPS를 넘었지만 답변이 짧고 비양자화 모델과 판정이 크게 달라 후보로 보지 않는다.

모든 결과는 30초 창 한 번의 탐색이다. 모델 크기·가중치 형식·평균 출력 길이가 서로 달라 모델 간 같은 조건의 우열 비교로 읽지 않는다. 의미 정답률은 확인하지 않았다.

## 측정 조건

- 300문항 풀(SHA-256 `67ca43b2…`), seed 20261002, context 4096, 출력 상한 512, temperature 0, thinking off.
- HTTP/1.1 스트리밍·keep-alive·재시도 0, 요청 timeout 120초.
- 각 동시 요청 단계는 warmup 뒤 30초 창이다. RPS는 창 안에서 끝난 정상 2xx 스트림만 센다. 지연·품질·실패율 합격선은 적용하지 않았다.
- U는 클라이언트 동시 요청 수, 설정 이름의 숫자는 엔진 내부 상한(Ollama `OLLAMA_NUM_PARALLEL`, llama.cpp `--parallel`, vLLM `--max-num-seqs`, SGLang `--max-running-requests`)이다.
- 한 번에 한 엔진만 올렸다. 시작 전과 종료 뒤에 같은 GPU에서 0 MiB·compute PID 없음을 연속 3회 확인했다.

- 엔진 이미지: `ollama/ollama:0.34.0`, `llm-frozen/llamacpp:20261002-bb4015809bc5`, `vllm/vllm-openai:v0.30.0`, `llm-frozen/sglang:20261002-f784a3df9ec0`. 실행기는 `llm-frozen/runner:20261002-fbc595f78605` 안에서 돌렸다.

Qwen 계열은 thinking을 끈 상태다. Ollama는 요청의 `think:false`와 실제 프롬프트 렌더 확인, llama.cpp는 공식 Qwen3 채팅 템플릿 파일과 `--reasoning off`, vLLM·SGLang은 `chat_template_kwargs.enable_thinking=false`를 썼다. Qwen3-14B 응답 1,345건에서 추론 내용이나 `<think>` 태그는 0건이었다.

Qwen3-4B 열은 2026-10-03 기본 측정([L4_SERVING_RESULTS_20261003.md](L4_SERVING_RESULTS_20261003.md))의 원시 요청을 같은 방식으로 다시 집계한 값이다. GPU 세션이 달라 같은 세션의 엄격한 비교는 아니다.

## 내부 상한을 바꿨을 때

Qwen3-8B와 EXAONE 3.5 7.8B는 상한을 32에서 64로 올려도 처리량이 거의 늘지 않았고 지연만 길어졌다.

| Qwen3-8B vLLM | 3.10 (U16) | 5.20 (U64) | 6.10 (U32) | 6.53 (U64) |

- 상한 16은 32보다 처리량이 15~30% 낮았다.
- Qwen3-8B vLLM은 상한 32·U32에서 6.10 RPS에 전체 지연 P95 8.6초, 상한 64·U64에서 6.53 RPS에 P95 14.5초였다.
- 동시 요청 수가 내부 상한을 넘으면 넘는 만큼 대기열에 선다. Qwen3-8B vLLM 상한 32에서 첫 토큰 중앙값은 U32가 0.15초, U64가 6.15초였다.

## 지연 구간

단계별 표에는 지연을 세 구간으로 나눠 적었다. 모두 클라이언트에서 잰 값이고 그 단계에서 시작해 성공한 요청 전체(측정 창 종료 뒤 완료한 요청 포함)의 중앙값과 P95다.

- **첫 토큰**: 요청을 보낸 시각부터 첫 내용 조각을 받은 시각까지. 대기열에서 기다린 시간이 여기에 들어간다.
- **첫 토큰→완료**: 첫 내용 조각부터 스트림 종료까지. 요청별로 `전체 − 첫 토큰`을 계산했다. 실제 생성에 걸린 시간에 해당한다.
- **전체**: 요청을 보낸 시각부터 스트림 종료까지.

구간별 중앙값·P95를 따로 구했으므로 첫 토큰과 첫 토큰→완료의 합이 전체와 정확히 같지는 않다. 서버 내부 대기 시간과 토큰별 시각은 수집하지 않았다.

## 답변 형식과 성향

형식 통과는 JSON 스키마와 근거 ID 존재 검사다. 의미 정답 판정이 아니다. 아래는 vLLM 상한 32에서 받은 응답을 문항별로 한 건씩 집계한 것이다.

- Qwen3-8B는 vLLM·SGLang 상한 8·16·32·64 전체 4,409건 가운데 전송 실패 1건을 뺀 4,408건이 모두 형식을 통과했다.
- Qwen3-8B와 Qwen3-14B는 같은 문항에서 근거 ID가 87% 일치했다. 다만 자료에 없는 내용을 물었을 때 4B·14B는 ABSTAIN으로, 8B는 대부분 CLARIFY로 처리했다. 상태값 일치는 54%다.
- EXAONE은 답변이 가장 길고 PARTIAL을 자주 썼다. 로컬 GGUF 측정에서 범위 밖 요청에 `OUT_OF_SCOPE`를 표시하고도 요청한 내용을 써 준 응답이 1건 있었다.
- Gemma 커뮤니티 AWQ 형식은 비양자화 BF16과 같은 문항에서 상태값이 62%, 근거 ID가 61%만 일치했다. BF16이 CLARIFY로 처리한 문항 상당수를 짧은 ANSWER로 답했고 근거 ID를 비운 답도 있었다. vLLM 로그상 `MarlinLinearKernel`로 적재됐고 가중치 메모리는 4.39 GiB(BF16 8.61 GiB)였다. 속도 수치는 실제 측정값이지만 같은 Gemma3 4B의 성능으로 쓰지 않는다.
- Gemma + SGLang은 출력 절단이 많았다. 상한 32에서 AWQ 형식 51건, BF16 38건이 출력 상한 512토큰에 닿았다. 원인은 확인하지 않았다.

## 실패와 조건 차이

**로드 실패**

- EXAONE + SGLang(상한 8·32): EXAONE의 `modeling_exaone.py`가 불러오는 `transformers.modeling_rope_utils.RopeParameters`가 고정 SGLang 이미지의 transformers 4.51.1에 없다. 로컬과 같은 원인이다. 상한 16·64는 실행하지 않았다.

**Gemma에서 바꾼 실행 조건**

- vLLM·SGLang의 dtype은 `bfloat16`이다. vLLM이 gemma3에 float16을 허용하지 않는다.
- SGLang attention 백엔드는 `flashinfer`다. Triton 백엔드가 Gemma의 window attention을 지원하지 않는다. Qwen·EXAONE의 SGLang 조건(Triton)과 다르다.

**llama.cpp 전송 실패**

재사용 소켓의 `socket hang up`이 요청의 36~43%에서 발생했다. Qwen3-8B 124/304건, Qwen3-14B 71/198건, EXAONE 103/262건, Gemma 173/402건이다. 기존 L4 측정과 같은 현상이며 이 실패가 섞인 llama.cpp RPS를 계산 성능으로 해석하지 않는다. 다른 엔진의 전송 실패는 Qwen3-8B vLLM 16의 1건뿐이다.

**Qwen3-14B Ollama 4**

세 번 시도했다. 측정된 값은 세 번째 시도이며 모든 단계가 표본 부족이다.

1. 첫 시도: Ollama가 9 GB GGUF를 컨테이너 저장소로 임포트하는 동안 사본이 여러 개 생겨 루트 디스크 여유가 21 GB에서 0.9 GB까지 줄었고 임포트가 실패했다. 같은 디스크에 기존 서비스의 PostgreSQL이 있어 실험 컨테이너를 수동으로 제거했다. 이때 실행기가 이미 다음 설정(llama.cpp)을 띄운 뒤여서 정상 기동 중이던 llama.cpp 컨테이너가 제거됐다. 이 run은 `cleanup_unverified`로 끝났고 잠금은 실행기 종료·실험 컨테이너 0개·GPU 0 MiB를 확인한 뒤 결과 폴더로 옮겼다. 기존 서비스에는 영향이 없었다.
2. 둘째 시도: 디스크 확보를 위해 AWQ 사본을 지운 뒤 실행했는데 실행기가 시작 시 AWQ 파일의 해시를 읽으려다 종료했다. 엔진은 기동하지 않았다. 이후 실행기를 선택한 설정이 쓰는 가중치만 해시하도록 고쳤다.
3. 셋째 시도: GGUF만 다시 받아 측정했다. 디스크 여유가 4 GB 아래로 내려가면 실험용 Ollama 컨테이너만 제거하는 감시를 함께 돌렸고 발동하지 않았다.

## 서버에서 바꾼 것

- 루트 볼륨이 128 GB로 늘어난 뒤 `growpart`와 `resize2fs`로 루트 파티션을 63 GB에서 123 GB로 확장했다. 재부팅은 없었다.
- `vllm/vllm-openai:v0.30.0` 이미지(약 32 GB)를 pull했고 서버에 남아 있다.
- 모델 파일은 `~/llm-bench/multimodel_20261006/model_assets/multimodel`에 받았다. 디스크가 좁아 측정이 끝난 모델의 서버 사본은 차례로 지웠다. 측정 종료 시점에 남은 것은 Qwen3-8B AWQ와 EXAONE AWQ다.
- 기존 서비스 네 개(`ubot-nginx`, `ubot-backend`, `ubot-postgres-1`, `ubot-ollama-1`)와 기존 이미지·볼륨은 건드리지 않았다. 419 GB 인스턴스 스토어는 쓰지 않았다.
- 측정 종료 시점: 실험 컨테이너 0개, GPU 0 MiB, 잠금 파일 없음, 루트 디스크 여유 28 GB.

**측정 설계**

- 설정·동시 요청 단계마다 30초 창을 한 번만 쟀다. 반복이 없어 회차 간 변동 폭을 모른다. 창 안 완료가 수십 건인 단계에서는 몇 건 차이로 RPS 순위가 바뀐다.
- 응답이 끝나야 다음 요청을 보내는 closed-loop 부하만 썼다. 응답과 무관하게 요청이 도착하는 open-loop 측정이 없어 지속 가능한 도착률을 말할 수 없다.
- 지연·품질·실패율 합격선을 적용하지 않았다. 설계 문서의 `C_SLO`·`λ_SLO`는 산출하지 않았고 `formal_benchmark_eligible=false`다.
- 느린 조합은 30초 창 안 완료가 20건에 못 미쳤다. Qwen3-14B의 Ollama 4와 llama.cpp 4는 모든 단계가 표본 부족이다.
- RPS는 창 안에서 끝난 요청만 세고 지연·실패·형식 통과는 창 종료 뒤 완료한 요청까지 포함한다. 두 값의 모집단이 다르다.
- 한 설정 안에서 동시 요청 단계를 작은 값부터 차례로 같은 서버 인스턴스에 걸었다. 앞 단계의 캐시 상태가 뒤 단계에 영향을 줬을 수 있고 단계 순서를 바꿔 확인하지 않았다. 설정 순서도 고정이었다.
- 문항은 300개 풀을 순환한다. 처리량에 따라 단계마다 실제로 쓰인 문항과 문항 수가 다르다. 느린 모델은 300문항을 다 돌지 못했다.
- 시험한 동시 요청 수는 설정마다 서너 단계뿐이다. 최고값은 시험한 단계 중의 관측값이며 그 사이나 바깥 값은 모른다.
- 장시간 부하에서의 안정성, 메모리 증가, 오류 누적은 보지 않았다. 모델 적재 시간과 재시작 시간도 비교하지 않았다.

**지연 측정**

- 모든 지연은 클라이언트에서 쟀다. 서버 내부 대기 시간과 토큰별 생성 시각은 수집하지 않았다.
- 첫 토큰은 첫 내용 조각을 받은 시각이다. 네트워크 조각은 토큰과 같지 않다.
- 첫 토큰→완료는 `전체 − 첫 토큰`이다. 순수 생성 시간 외에 스트림 전송과 클라이언트 처리 시간이 들어 있다.
- 구간별 중앙값·P95를 따로 구했으므로 구간 값을 더해 전체 지연을 재구성할 수 없다.
- 부하 생성기가 엔진과 같은 호스트(8 논리 코어)의 컨테이너에서 돌았다. 네트워크 지연이 없고 클라이언트가 서버와 CPU를 나눠 썼다. 동시 요청 수가 큰 단계에서 클라이언트가 병목이었는지 확인하지 않았다.

**환경**

- 기존 서비스 네 개가 같은 호스트에서 떠 있는 채로 쟀다. GPU는 0 MiB에서 시작했지만 CPU·디스크·메모리는 격리하지 않았다.
- Qwen3-4B 열은 2026-10-03의 다른 GPU 세션 값이다. 당시 GPU UUID(`GPU-c79379fa…`, `GPU-cd3de85b…`)와 오늘(`GPU-6c5b0c97…`)이 다르고 그 사이 인스턴스가 재시작됐으며 루트 볼륨이 확장됐다. vLLM 이미지 ID(`sha256:8a69ffad…`)는 같다.
- 오늘 측정도 한 번에 이어서 돌지 않았다. 모델 파일을 받고 지우기를 반복했고 Qwen3-14B는 run이 한 번 중단됐다. 가중치 해시는 받을 때마다 확인했다.
- 실행기 코드가 측정 도중 여러 번 바뀌었다(Linux 지원, 모델·상한 설정 추가, 해시 대상 수정). run마다 쓰인 실행기 버전이 다르고 `load_test_v2`와 달리 소스 지문을 고정하거나 run에 기록하지 않았다. 측정 로직 자체는 `load_test_v2` 라이브러리를 그대로 쓴다.
- L4 한 장의 결과다. 다른 GPU나 여러 장 구성으로 환산하지 않는다.

**모델과 가중치**

- 모델 크기가 서로 다르다(4B·7.8B·8B·14B). 모델 간 RPS 차이에는 크기 차이가 들어 있다.
- 엔진 그룹마다 가중치 형식이 다르다. Ollama·llama.cpp는 GGUF Q4_K_M, vLLM·SGLang은 AWQ 또는 BF16이다. 엔진 간 차이에 양자화 방식 차이가 섞여 있다.
- 공식 GGUF와 공식 AWQ가 같은 상위 체크포인트에서 변환됐는지는 모델 카드 선언만 확인했다. 변환 계보를 검증하지 않았다.
- Gemma는 구글 공식 저장소가 승인제여서 받지 못했다. GGUF는 `ggml-org` 변환본, BF16은 가중치 해시가 공식과 같은 `unsloth` 미러, AWQ 형식은 QAT INT4 체크포인트를 옮긴 개인 변환본이다. 세 가지가 서로 다른 출처다.
- Qwen3-8B·14B의 llama.cpp 채팅 템플릿은 Qwen3-4B-AWQ에서 추출한 파일을 썼다. 크기별 공식 템플릿과 같은지 대조하지 않았다.
- Ollama는 GGUF 메타데이터에서 템플릿을 자동으로 정했다. EXAONE·Gemma에서 그 템플릿이 공식 채팅 템플릿과 같은 프롬프트를 만드는지 확인하지 않았다.
- 평균 출력 토큰 수는 각 엔진이 보고한 값이고 모델마다 토크나이저가 다르다. 모델 계열이 다르면 토큰 수를 직접 비교할 수 없다.

**엔진 설정**

- 엔진마다 설정 한 가지씩만 썼고 튜닝하지 않았다. vLLM GPU 메모리 비율 0.8, SGLang 0.7, KV 캐시 형식 등은 Qwen3-4B 실험의 값을 그대로 가져왔다. 모델마다 더 나은 설정이 있을 수 있다.
- Ollama·llama.cpp는 내부 상한 4만 쟀다. 상한 16·64는 Qwen3-8B와 EXAONE의 vLLM·SGLang에만 적용했다.
- SGLang은 상한을 바꿀 때 CUDA graph 최대 배치도 같이 바꿨다. 상한 한 변수의 효과로 분리할 수 없다.
- Gemma는 dtype과 SGLang attention 백엔드가 다른 모델과 다르다. Gemma의 SGLang 결과를 Qwen의 SGLang 결과와 같은 조건으로 볼 수 없다.
- EXAONE의 SGLang은 버전 호환성 때문에 측정하지 못했다. 성능이 낮다는 뜻이 아니다.
- llama.cpp는 재사용 소켓 실패가 요청의 36~43%였다. 성공한 요청만으로 계산한 RPS이며 전송 문제를 고치기 전에는 llama.cpp의 계산 성능을 말할 수 없다.
- 엔진 버전이 고정돼 있고 엔진마다 시점이 다르다. SGLang 0.4.6.post5는 vLLM v0.30.0보다 오래된 버전이다. 최신 버전끼리의 비교가 아니다.
- 모든 요청에 JSON 스키마 구조화 출력을 걸었다. 엔진마다 제약 디코딩 구현이 달라 그 비용이 처리량에 다르게 들어갔을 수 있다. 구조화 출력을 끈 측정은 없다.
- 생성 조건은 context 4096, 출력 상한 512, temperature 0, thinking off 하나뿐이다. thinking을 켠 Qwen, 더 긴 문맥, 다른 출력 상한에서는 수치가 달라진다.

**답변 품질**

- 의미 정답률을 확인하지 않았다. 문항에 정답이 없다.
- 형식 통과는 JSON 스키마와 근거 ID가 입력 자료에 존재하는지만 본다. 근거가 답과 맞는지, 답이 사실인지는 보지 않는다.
- 상태값 분포와 근거 ID 일치율은 모델 간 차이를 기술할 뿐이다. 어느 모델의 판정이 옳은지 판정하지 않았다.
- 문항별 집계는 vLLM 상한 32 한 설정의 응답이고 모델마다 집계 문항 수가 다르다(182~300). 같은 문항 집합의 비교가 아니다.
- 본문에 든 개별 답변 사례는 눈으로 고른 것이다. 빈도를 대표하지 않는다. EXAONE이 범위 밖 요청에 응한 사례는 로컬 GGUF에서 본 1건이다.
- 이 테스트의 프롬프트는 CLARIFY 상태를 허용하는 예전 형식이다. CLARIFY가 없는 v4 프롬프트에서의 상태값 분포는 다를 수 있다.
- 문항은 통신 상담 FAQ 300개다. 실제 서비스 질문 분포나 입력 길이 분포를 대표한다는 근거가 없다.
- Gemma + SGLang의 출력 절단이 많은 원인을 확인하지 않았다.

**운영 판단**

- 8 RPS는 탐색용 목표이며 운영 요구에서 나온 값이 아니다. "6 RPS면 충분한가"는 예상 동시 사용자와 허용 지연이 정해져야 답할 수 있다.
- 비용, 가용성, 장애 복구, 여러 인스턴스 구성은 다루지 않았다.
