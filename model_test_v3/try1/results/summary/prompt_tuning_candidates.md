# 저급 모델 프롬프트/코드 제어 튜닝 후보 선정

생성일: 2026-09-30 · 근거: [test2(v2 try2) `hallucination_cause.md`](../../../../model_test_v2/try2/results/summary/hallucination_cause.md) · [test3(v3 try1) `hallucination_cause.md`](hallucination_cause.md) · 두 문서의 원인 분류(A/B/P/S/M)와 13개 문항 유형 집계를 그대로 인용해 "무엇으로(프롬프트든 코드든) 고치기 쉬운가"를 재해석한다.

## 0. 결론 먼저

- **제어 수단을 프롬프트로 한정하지 않지만, "코드로 가능"을 함부로 상(上)으로 치지 않는다.** 코드 개입이 통하려면 **모델의 판단 없이도 이미 알 수 있는 신호**가 있어야 한다. 그 신호가 이미 존재/확인된 경우만 상(上)으로 두고, 새로 만들어야 하는 경우는 "중상"으로 낮춘다.
- **운영 시스템은 이미 임베딩 유사도 검사를 하고, 임계값을 넘는 문서만 컨텍스트로 받는다.** 이 평가(test2·test3)는 문항마다 context를 미리 정해서 주는 방식이라 이 임베딩 단계를 거치지 않았다. 그래서 **"무관 FAQ(HR)" 유형의 실패 대부분은 운영 파이프라인에 이미 있는 검사와 모델을 결합하기만 하면 사라질 가능성이 크다** — 새 인프라가 아니라 기존 임베딩 단계와의 "결합" 문제다. 이 문서에서는 이런 항목의 개선 방법을 **"임베딩 도입"**으로 명시한다.
- **다만 "유사하지만 답 없음(SR)"·"유사 FAQ 노이즈(NC)"는 임베딩으로 해결되지 않는다.** 이 두 유형에 있는 문서는 **정의상 이미 임베딩 임계값을 통과할 만큼 유사해서 컨텍스트에 들어온 것**이다. 임베딩은 "무관한 걸 거르는" 도구라서, "유사하지만 실제로는 답이 없는 문서"는 걸러내지 못한다. 이 유형의 판단 오류(B1)는 임베딩 도입 이후에도 그대로 남는다 — 다섯 모델을 가르는 핵심이 바로 이 지점이다.
- **저급 모델 후보는 `gemma3:4b` · `exaone3.5:7.8b` · `qwen3:1.7b` · `qwen3:4b`(OFF) · `qwen3:8b`(OFF) 다섯이다.** `qwen3:4b`·`qwen3:8b`는 ON을 운영 후보에서 배제하기로 정했으므로 이 문서도 OFF 결과만 쓴다.
- **SR 유형에서 분류된 것 중 순수 판단 오류(B1)가 차지하는 비중으로 다섯 모델을 줄 세우면:**
  - **gemma3:4b**: 31건 중 B1 **0건** — 전부 ABSTAIN↔CLARIFY 교차(스펙 공백, 임베딩과 무관하게 프롬프트 정의만으로 해소).
  - **qwen3:8b (OFF)**: 14건 중 B1 **0건** — 전부 교차. gemma3:4b와 동률로 가장 양호하다.
  - **exaone3.5:7.8b**: 21~28건 중 B1 3~10건(14~36%) — 교차(16~18건)는 프롬프트로 해소되지만 B1은 모델 능력 문제로 남는다.
  - **qwen3:4b (OFF)**: 11건 중 B1 3건(27%).
  - **qwen3:1.7b**: 18~27건 중 B1 16~22건(89~91%) — 압도적으로 나쁘고, 임베딩·프롬프트·코드 어느 것도 안 통한다.
- **결론: 공동 1순위 `gemma3:4b`·`qwen3:8b`(OFF), 3순위 `exaone3.5:7.8b`, 4순위 `qwen3:4b`(OFF), 비추천 `qwen3:1.7b`.** 이 순위는 환각(A/B/P) 데이터만 근거로 했다. 5.6절에서 환각이 없는 status 오류(S)의 방향(과대/과소)으로 다시 확인해도 같은 결론이 나온다 — qwen3:1.7b만 유일하게 "과대"(과신) 쪽이고 나머지 넷은 "과소"(과잉 보류) 쪽이다. M(내용 누락)은 문항 품질 문제가 커서 순위에 넣지 않았다.
- **코드 개입에는 대가가 있다(1.5절).** 검색 결과 0건 차단(EC)·임베딩 결합(HR)·API 값 템플릿(AR)만 순수 이득이거나 이미 있는 인프라 재사용이다. B3 grounding 검증·리트리버 재순위화·인젝션 분류기·슬롯 추출은 **별도 모델 추론을 하나 더 얹는 쪽**이라 지연이 늘고 VRAM(동시 처리량) 손해로 번질 수 있다.

## 1. 목적과 개선 여지 기준

**목적**: 저급 모델 중 프롬프트·코드 제어(파인튜닝 없이)로 개선 여지가 큰 모델을 골라, 먼저 시도할 대상을 정한다.

**저급 모델 후보**: [`model_selection.md`](model_selection.md)의 2단계(86,400가지 전수) 결과 최종까지 생존한 건 `qwen3:14b`(ON 17.3%·OFF 97.0%)와 `gemma3:12b`(82.7%) 둘뿐이다. 나머지 5개 설정 — `gemma3:4b`(0.0%) · `exaone3.5:7.8b`(0.0%) · `qwen3:1.7b` ON/OFF(둘 다 0.0%) · `qwen3:4b` ON(0.0%)·OFF(1.9%) · `qwen3:8b` ON(0.0%)·OFF(1.1%) — 는 전부 1차 MVP 선정에서 탈락했다. `qwen3:4b`·`qwen3:8b`는 운영 후보에서 이미 ON을 배제하기로 했으므로 **이 문서에서는 OFF 결과만 다룬다.** `qwen3:14b`·`gemma3:12b`만 비교 기준선으로 남긴다.

**제어 수단과 "필요 전제조건"**

| 수단 | 설명 | 신뢰도 |
|---|---|---|
| 코드 — 전제조건 확인됨 | 신호가 하니스/운영 시스템에 **이미 있다고 확인된** 경우 (검색 결과 0건 여부, evidence_ids, **임베딩 유사도 검사+임계값** — 운영 파이프라인에 이미 있음) | 높음 — 상 등급 근거 |
| 코드 — 전제조건 미확인/신규 구축 필요 | 신호(FAQ 메타데이터, 사용자 속성 태깅, 대화 슬롯, 구조화 API 값, 필수 항목 스키마)를 **새로 노출·구축해야** 함 | 중간 — "중상"으로 한 단계 낮춤 |
| 프롬프트 | system/instruction에 규칙·정의·예시를 추가 | 모델 성능에 의존 |
| 모델 능력 | 코드·프롬프트 어느 쪽도 안 통한다. 임베딩 임계값을 이미 통과한 문서인데 실제로는 답이 없는 경우처럼, 문맥을 이해해서 가려야 하는 문제 | 낮음 — 하 등급 |

**개선 여지 등급**: 상 / 중상 / 중 / 하(모델 능력 문제) / 해당없음(문항·표본 문제).

## 1.5 코드 개입 메커니즘과 트레이드오프

| 메커니즘 | 정확히 무엇을 하는가 | 적용 항목 | 트레이드오프 | 비용 성격 |
|---|---|---|---|---|
| 빈 컨텍스트 사전 차단 | 검색 결과 개수를 세어 0건이면 **모델을 호출하지 않고** 즉시 ABSTAIN 반환 | EC, B1(EC 기원) | 없음 — LLM 호출을 생략하므로 지연·GPU 비용이 **줄어든다** | 순이익 |
| **임베딩 유사도 결합** | 리트리버가 이미 계산하는 유사도 점수·임계값 검사를 모델 앞단에 그대로 연결 — **새로 만드는 게 아니라 운영 파이프라인과 결합**하는 것 | HR, B1(HR 기원), 판정불가 중 ABSTAIN↔OUT_OF_SCOPE(HR 유래분) | 결합 비용은 낮다(이미 운영 중인 검사). 다만 **임계값을 보수적으로 잡으면 진짜 답이 있는 질문도 걸러내는 재현율 손실**이 있고, 이건 이 문서가 아니라 운영 중인 리트리버의 기존 튜닝 문제다 | 결합 비용 낮음 + 기존 정확도 트레이드오프 |
| (참고) 임베딩이 통하지 않는 경우 | "유사하지만 답 없음(SR)"·"유사 FAQ 노이즈(NC)"의 문서는 **정의상 이미 임계값을 통과**해서 컨텍스트에 들어온 것들이다 | SR, NC | 임베딩은 "무관한 걸 거르는" 도구라 "유사하지만 답이 없는" 문서는 걸러내지 못한다 — 근본적으로 다른 신호(문맥 이해)가 필요하다 | 개선되지 않음 |
| API 값 템플릿 삽입 | API 응답 필드를 답변 템플릿에 직접 삽입, 모델은 문장만 포장 | AR | API 호출 자체는 기존 파이프라인에 이미 있는 지연이라 추가 비용이 거의 없다 | 거의 없음 |
| evidence_ids 대조 (grounding validator) | 답변 생성 후 각 주장을 `evidence_ids`가 가리키는 FAQ와 **NLI 모델로 대조**, 불일치 시 재생성 요청 | B3 | ① **NLI 모델을 답변마다 다시 추론**해야 해서 응답당 지연이 늘어난다. ② NLI 모델을 GPU에 상시 로드해야 하므로 **VRAM 점유가 늘어난다** — `vram_results.md` 기준 후보 모델들이 이미 Tesla T4 16GB 중 상당 부분을 쓰고 있어(최대 9.88GB, 여유 6.12GB), 여기에 얹으면 **동시 처리량이 줄어들 수 있다.** ③ 불일치가 감지되면 재생성 루프가 돌아 **최악의 경우 LLM을 두 번 호출 — 지연이 거의 2배** | 지연 + VRAM(동시성) + 최악 2배 재생성 |
| FAQ 메타데이터(시행일) 비교 | FAQ 문서에 시행일 필드를 태깅해두고, 같은 대상에 여러 FAQ가 걸리면 최신 것을 코드가 선택 | CF | 태깅 자체는 일회성 비용이지만, **FAQ가 갱신될 때마다 시행일 필드도 같이 유지보수해야 한다** | 운영·유지보수 |
| 조건 룰 엔진 | 요금제 조건·기준값을 결정론적 규칙(if-else, 룰 테이블)으로 별도 구현해 모델 대신 계산 | CE | **FAQ 본문과 룰 엔진이라는 두 개의 진실 소스가 생긴다.** 둘이 어긋나면 오히려 새로운 환각(B3) 원인이 된다 | 이중 유지보수 |
| 사용자 세그먼트 사전 필터링 | FAQ에 적용 대상(요금제·세그먼트) 태그를 달아 검색 전에 후보를 줄임 | UI | 검색 대상이 줄어 지연은 오히려 준다. 다만 **태깅이 틀리거나 한 FAQ가 여러 세그먼트에 걸치면 정답 FAQ가 통째로 빠질 수 있다**(재현율 손실) | 정확도 트레이드오프 |
| 필수 항목 커버리지 계산 | 질문 유형별 "필수 필드" 스키마를 만들고, 컨텍스트에서 몇 개가 확인됐는지 세어 status를 결정 | PI(B2), B4, S-과소 | 단순 키워드 매칭이면 저비용이지만, 자연어 조건은 결국 **작은 추출 모델이나 LLM 재호출이 필요할 수 있어 grounding validator와 같은 지연·VRAM 문제**가 생긴다 | 지연(스키마 복잡도에 비례) |
| 대화 슬롯 트래커 | 이전 턴에서 확정된 값을 추출해 세션에 저장하고, 다음 턴 시스템 메시지에 주입 | MT | **세션 상태를 서버에 저장해야 한다** — 동시 사용자가 많아지면 상태 저장소(Redis 등)가 필요해지고 확장성 고려가 추가된다 | 저장소·확장성 + 지연 |
| 인젝션 탐지기 | context 텍스트에서 지시문 패턴을 정규식 또는 분류기로 탐지·제거 | AD | 정규식이면 저비용이지만 새 패턴에 취약. **분류기 기반이면 매 요청마다 추가 모델 추론이 붙어 지연이 늘어난다** | 낮음(정규식) 또는 지연(분류기) |
| 리트리버 recall 확대·재순위화 | top-k를 늘리거나 별도 rerank 모델로 재정렬, 중복 FAQ 병합 | MC, NC | top-k 확대는 **컨텍스트 토큰이 늘어 지연이 늘어난다.** rerank 모델을 쓰면 **별도 모델 추론이 하나 더 붙어 지연·VRAM 부담이 함께 늘어난다.** 이미 P95 지연이 상담봇 기준(3~5초)을 넘는 후보(`qwen3:14b OFF` 8.11s)에는 부담이 크다 | 지연 + VRAM |

**요약**: 진짜 "무료"이거나 이미 있는 걸 재사용하는 건 빈 컨텍스트 차단·임베딩 결합·API 값 템플릿 셋뿐이다. grounding 검증·재순위화·인젝션 분류기·슬롯 추출은 별도 모델/로직을 추가로 돌리는 쪽이라 지연과 VRAM을 갚아야 한다. 룰 엔진·메타데이터 태깅·세그먼트 필터링은 실행 비용은 낮지만 이중 유지보수나 재현율 손실 위험이 있다.

## 2. 환각 원인 코드별 제어 수단과 개선 여지

| 코드 | 이름 | 제어 수단 | 필요 전제조건 / 확인 여부 | 개선 여지 | 트레이드오프(1.5절) | 근거 |
|---|---|---|---|---|---|---|
| A1 | 자각 후 위반 | 프롬프트 | 없음 | **상** | 없음 | 상태 판단은 이미 맞았고 본문에서만 샌다 |
| A2 | 명시적 보충 | 프롬프트 | 없음 | **상** | 없음 | 모델이 스스로 "정보 부족"이라 쓰고도 채운다 |
| B3 | 근거 혼동 | 프롬프트(원문 인용) + 코드(grounding validator) | evidence_ids·NLI 채점기 — 이미 있음 | 중상 | 지연 + VRAM + 최악 2배 재생성 | 사후 검증기로 상당수 잡을 수 있으나 근본은 식별 능력 문제 |
| B4 | 과소 판단 | 프롬프트(임계값 규칙) + 코드(커버리지 계산) | 필수 항목 스키마 — 미확인 | 중상 | 지연(스키마 복잡도에 비례) | "무엇을 세야 하는지" 스키마가 아직 없다 |

## 5. 모델별 × 13개 유형 개선 여지 매트릭스

**표기 규칙**: "지배 원인"은 원문에 구체적으로 적힌 것만 정확히 표기한다. 크게 세 갈래다 — ① **ABSTAIN↔CLARIFY 교차**(빈 컨텍스트·유사 문서에서 "물어야 할지 보류해야 할지" 혼동), ② **ABSTAIN↔OUT_OF_SCOPE 교차**(무관 FAQ에서 "보류해야 할지 범위 밖이라 안내해야 할지" 혼동), ③ **미해당(CONFLICT 처리 불가)**(FAQ 충돌 등에서 결정 트리 자체가 다루지 않는 조합) — 이 셋은 서로 다른 문제이므로 원문이 구분한 곳만 구분해 적고, 원문이 세부 유형을 밝히지 않은 곳은 **"교차(세부 미기재)"**로 정직하게 남긴다. ### 5.7 5.1~5.5절 S·M 열의 계산 방법과 오차 범위

5.1~5.5절의 S·M 숫자는 두 `hallucination_cause.md`에 없는, 이 문서를 위해 원본 LLM Judge 판정을 다시 집계한 값이다. 재현 가능하도록 규칙을 적는다.

- **원본 데이터**: test2는 `model_test_v2/try2/results/summary/review_all_models_V2.csv`(문항별 유형·기대 상태·모델 상태·status_일치·AI_정확도·AI_근거점수를 한 행에 다 가진 통합 CSV). test3는 `model_test_v3/try1/results/llm_judge/{t0_think,t0_nothink}/*.md`의 `<details>` 문항별 블록(원본 요청 JSON + AI 판정 JSON)을 파싱했다. 두 경로 다 고유 300문항(실행회차 1)만 썼다.
- **분류 순서**: `hallucination_cause.md`와 같다. ① C 문항(각 라운드 고유 13개) 제외 → ② AI_근거점수 1~3점은 환각(이미 5.1~5.5절의 "환각" 열에 있으므로 S·M 대상에서 제외) → ③ AI_정확도가 CORRECT면 제외(⑤·⑥ 칸) → ④ 남은 INCORRECT 중 status_일치=true면 **M**, false면 **S** → ⑤ S는 기대·실제 status의 서열(ANSWER 3 > PARTIAL 2 > CLARIFY/ABSTAIN/OUT_OF_SCOPE 1)을 비교해 실제가 높으면 **과대**, 낮으면 **과소**, ABSTAIN↔CLARIFY·ABSTAIN↔OUT_OF_SCOPE 교차나 CONFLICT가 걸리면 표에는 안 적고 "기타"로만 처리했다(원인 표의 교차·미해당과 중복 집계하지 않기 위해).
- **M "공통·개별" 기준**: `gemma3:4b`(test2)·`exaone3.5:7.8b`(test2)·`qwen3:1.7b`(test2)·`qwen3:4b`(OFF)·`qwen3:8b`(OFF) 다섯 개 데이터 포인트를 하나의 기준 집합으로 놓고, 같은 문항 ID가 이 다섯 중 3개 이상에서 M으로 나오면 "공통", 아니면 "개별"이다. **이 기준 집합은 라운드(test2 vs test3)를 섞었다** — test_set2의 300문항 ID·필수 사실이 v2·v3에서 동일해(`CLAUDE.md`) 라운드가 달라도 "이 문항을 모델들이 공통으로 빠뜨리는가"는 유지된다고 보았다. `qwen3:1.7b`의 ON·OFF 열이나 `gemma3:4b`·`exaone3.5:7.8b`의 test3 열에 나온 M도 **같은 기준 집합에 있는 문항 ID인지로 공통·개별을 판정**했다(그 열 자체는 기준 집합에 들어가지 않았다).
- **오차 범위**: 모델별 합계가 두 `hallucination_cause.md`의 7.2절 수치와 1~3건 차이 나는 경우가 있다(예: gemma3:4b test2 S 합계 57 vs 재계산 59). 원인은 소수 문항의 상태 값이 빈 문자열이거나 대소문자가 다른 것으로 확인했다("기타"로 흡수됨). 유형별 경향과 상대적 크기를 읽는 데는 영향이 없는 수준이다.
- **참고하지 않은 것**: `gemma3:12b`·`qwen3:14b`·`qwen3:4b`/`qwen3:8b`의 ON 라운드는 5.1~5.5절 어디에도 없다(1절의 후보 정의에 따름). M "공통" 기준 집합도 이 5개 데이터 포인트로 고정했다 — 본래 `hallucination_cause.md`가 쓴 기준(test2는 5개 모델 중 3개, test3는 7개 모델 중 4개)과는 다른, 이 문서만의 정의다.

## 7. 한계
