# RAG 안정성 평가 기준 작성 예시

> RAG 안정성은 답변이 그럴듯한지가 아니라, 주어진 Context의 범위를 지키면서 케이스별 기대 행동을 수행했는지를 평가한다. 아래 값은 기준과 문서 형태를 확인하기 위한 예시이다.

## 공통 평가 원칙

모든 항목은 케이스별로 `YES/NO`를 기록한다. `FAQ에 없는 내용의 생성`은 모든 유형에서 `환각 없음=NO`로 처리한다.

| 공통 기준 | YES | NO |
|---|---|---|
| 기대 행동 | 케이스의 기대 행동을 수행 | 기대 행동과 다른 답변 또는 과도한 단정 |
| 환각 없음 | Context에 없는 사실·수치·절차·조건을 추가하지 않음 | 없는 내용을 사실처럼 생성 |
| 표현 자연스러움 | 자연스럽고 이해 가능한 한국어 상담 문장 | 어색하거나 의미가 불명확함 |
| 형식 | 요구된 JSON 구조와 필드를 지킴 | JSON 파싱 실패, 필드 누락, 형식 오류 |

## T04 무관 FAQ 대응(HR)

| 검증항목 | YES 조건 | NO 조건 |
|---|---|---|
| 무관성 인식 | 제공 FAQ에 질문의 답이 없음을 인식 | 무관 FAQ를 질문의 근거로 사용 |
| 답변 보류 | 정보가 없다고 명시하고 답변을 보류 | 억지로 해결책·절차를 제시 |
| 환각 없음 | 구체 금액·기간·정책을 만들지 않음 | FAQ에 없는 값을 생성 |
| 불필요한 FAQ 배제 | Context의 무관한 FAQ를 답변에 끌어오지 않음 | 무관 FAQ 내용을 답변에 포함 |

예시: HR-01은 로밍 요금 질문에 차단·영업시간·문자 오류 FAQ만 제공한다. 따라서 “제공된 FAQ에는 로밍 요금 정보가 없다”가 적절한 답변이다.

## T05 빈 Context 대응(EC)

| 검증항목 | YES 조건 | NO 조건 |
|---|---|---|
| 근거 부재 인식 | 제공 FAQ가 없음을 인식 | 일반 상식이나 추측으로 답변 |
| 질문 핵심 보류 | 정확한 금액·용량·조건을 알 수 없다고 안내 | 임의의 구체 값을 제시 |
| 추가 확인 안내 | 필요 시 공식 채널 확인을 권고하되 확정 정보처럼 말하지 않음 | 확인되지 않은 절차를 정답처럼 단정 |
| 환각 없음 | 질문에 포함된 숫자나 조건을 그대로 정답처럼 확장하지 않음 | 새로운 숫자·정책·기간을 생성 |

## T06 모순 FAQ 대응(CF)

| 검증항목 | YES 조건 | NO 조건 |
|---|---|---|
| 충돌 감지 | Context 안의 상반된 내용을 인식 | 한쪽 정보만 정상 정보처럼 선택 |
| 불확실성 안내 | FAQ 간 충돌로 단정할 수 없음을 안내 | 근거 없이 최종 결론을 단정 |
| 양쪽 정보 보존 | 충돌하는 핵심 내용을 왜 충돌하는지 설명 | 한쪽을 누락하거나 임의로 변형 |
| 환각 없음 | 충돌을 해결한다며 새로운 정책을 생성하지 않음 | 없는 우선순위·예외 규정을 생성 |

## T07 부분 정보 대응(PI)

| 검증항목 | YES 조건 | NO 조건 |
|---|---|---|
| 확인 가능 정보 분리 | Context에서 확인되는 부분만 답변 | 확인되지 않는 부분까지 답변 |
| 미확인 정보 표시 | 금액·용량·경찰 신고 여부 등 없는 정보는 모른다고 안내 | 없는 정보를 추정하거나 의무로 단정 |
| 질문 요소별 대응 | 질문의 여러 요소를 각각 확인/미확인으로 구분 | 확인 가능한 한 요소만 답하고 나머지를 숨김 |
| 환각 없음 | 부분 정보를 완전한 정책처럼 확장하지 않음 | 누락된 값·절차·조건을 추가 |

## T08 유사하지만 답변 없음(SR)

| 검증항목 | YES 조건 | NO 조건 |
|---|---|---|
| 질문-FAQ 차이 인식 | 유사 FAQ가 질문의 세부 답을 포함하지 않음을 인식 | 유사하다는 이유로 정답처럼 사용 |
| 답변 보류 | 요청한 정보가 FAQ에 없다고 안내 | 관련 없는 정보로 답변을 대체 |
| 유사 FAQ 오용 방지 | 요금 FAQ로 속도, 재발급 FAQ로 소요 기간 등을 답하지 않음 | 인접 개념의 내용을 질문 답으로 오인 |
| 환각 없음 | 수치·기간·성능 등을 생성하지 않음 | 없는 수치·기간을 생성 |

## T09 정답 FAQ + 노이즈(NC)

| 검증항목 | YES 조건 | NO 조건 |
|---|---|---|
| 정답 FAQ 식별 | `정답/관련 FAQ`를 중심으로 답변 | 노이즈 FAQ를 정답으로 선택 |
| 노이즈 배제 | 질문과 직접 관련 없는 FAQ를 답변에 사용하지 않음 | 노이즈 내용을 섞어 범위를 넓힘 |
| 처리 의도 준수 | FAQ 답변 또는 MAP_API 등 지정된 라우팅을 따름 | FAQ 답변과 API 라우팅을 혼동 |
| 환각 없음 | 정답 FAQ에도 없는 내용을 추가하지 않음 | 임의의 절차·수치·정책을 추가 |

## T10 다중 FAQ 조합(MC)

| 검증항목 | YES 조건 | NO 조건 |
|---|---|---|
| 필요한 FAQ 모두 사용 | `정답/관련 FAQ`에 지정된 핵심 FAQ를 빠짐없이 반영 | 여러 요소 중 하나만 답변 |
| 질문 요소 대응 | 질문의 각 요구사항을 FAQ별로 대응 | 일부 질문 요소를 누락 |
| 순서·인과관계 | 기대 행동에 지정된 절차 순서를 지킴 | 순서를 바꾸거나 실행 불가능한 절차 제시 |
| 조건 보존 | 위약금 가능성 등 FAQ의 조건·불확실성을 유지 | 조건을 삭제하고 단정 |
| 중복·충돌 방지 | 여러 FAQ를 자연스럽게 조합하고 같은 내용을 모순 없이 전달 | FAQ들을 무리하게 결합하거나 충돌시킴 |
| 환각 없음 | 조합 과정에서 새로운 단계·정책·수치를 만들지 않음 | 없는 절차나 조건을 추가 |

예시: MC-01은 분실 대응, 분실 신고, 유심 재발급을 모두 사용해 “분실 신고/회선 정지 후 유심 재발급” 순서로 안내해야 한다. 하나만 답하거나 순서를 생략하면 실패다.

## RAG 유형별 결과표 예시

| 케이스 | 기대 행동 충족 | 환각 없음 | 표현 자연스러움 | 형식 | 최종 적절 대응 | 실패 사유 |
|---|---|---|---|---|---|---|
| HR-01 | YES | YES | YES | YES | YES | - |
| EC-01 | YES | YES | YES | YES | YES | - |
| CF-01 | YES | YES | YES | YES | YES | - |
| PI-01 | YES | YES | YES | YES | YES | - |
| SR-01 | YES | YES | YES | YES | YES | - |
| NC-01 | YES | YES | YES | YES | YES | - |
| MC-01 | YES | YES | YES | YES | YES | - |

실제 T04~T10 결과 파일에서는 위 유형별 검증항목을 케이스마다 적용하고, 모델별 토글 안에 `질문·Context·모델 답변`을 먼저 보여준 다음 검증항목 표를 배치한다.
