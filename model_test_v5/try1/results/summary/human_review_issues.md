## 1. PI — 질문이 많을 때 누락·환각

Q4 PI 100건을 기대 상태·정답 근거 FAQ 수·난이도로 나눴다.

| 근거 FAQ 수·난이도 | 정답 | 누락 있음 | 환각 있음 |
|---|---|---|---|
| 1개, Easy·Medium | 31/33 | 2 | 5 |
| 2개, Medium | 28/37 | 9 | 15 |
| 2개, Hard (답할 수 없는 질문이 하나 더 붙음) | **14/30** | 15 | 13 |

Hard 오답은 두 가지다.
- **답할 수 없는 부분을 채움**: PI-0141~0149 "경찰 신고는 의무가 아니며, 기한도 없습니다". PI 환각 유형은 UNSUPPORTED_GENERALIZATION 21 · FABRICATION 17.
- **답할 수 있는 부분까지 통째로 보류**: PI 오답 27건 중 11건이 ABSTAIN. PI-0171은 마지막 질문(자동 재전송)만 "자료에 없다"고 하고 앞의 FAQ 두 개를 건너뛰었다.

### FAQ-087 "지원되는 가입 채널"

- 이 FAQ가 정답 근거인 7문항 × 3모델 = 21개 답변에서 "채널" 조건을 11번 빠뜨렸고 그중 10번이 오답이었다.
- "지원되는 가입 채널"이 어떤 채널인지 정의가 없어 모델이 꾸밈말로 보고 뺀다.
- **Judge 일관성 문제**: PI-0111과 PI-0112의 Q4 답변은 둘 다 "본인 인증 후 비대면 개통이 가능합니다"로 채널을 똑같이 뺐는데, 0111은 정답, 0112는 오답이다.

## 2. MC-0116 — FAQ-913이 자기 질문에 답하지 않음

- FAQ-913 질문은 "인터넷 요금도 휴대폰과 같은 날 청구되나요?"인데 답변은 "기본 납부일은 매월 21일이며 자동이체는 …"뿐이다. 같은 날인지는 없다.
- MC-0116: Q4·Q8은 "같은 날 청구됩니다" → 오답(근거 없는 확정), QAT는 질문을 되풀이하고 납부일만 말해 정답.
- **MC-0148**: Q4·Q8은 "같은 날 청구되지 **않습니다**" → 이것도 오답.
- 결론: Judge는 근거 기준을 지켰다. 문제는 FAQ다. 모델은 이 질문을 안정적으로 추론하지 못하고, 엄격한 근거 기준에서는 어느 쪽으로 답해도 창작이 된다. 실제 정책은 "같은 날"(사람 검토).
- 같은 유형: FAQ-819("유지하려면 어떻게 해야 하나요?"에 기준 금액만 답함). 예/아니요 질문인데 답에 예/아니요가 없는 FAQ는 전수 점검이 아직 남았다.

## 3. AR

### 3-1. is_open 오인

Q4 AR 오답 48건 중 23건이 영업 여부를 잘못 읽은 경우다(Judge 사유에 "영업 중이 아닌·영업 종료·닫힌" 등).
- **false를 "영업 중"으로 읽음**: AR-0014 "가장 가까운 영업 중 매장은 가상 누리4점(115m)"(is_open false).
- **false를 "미확인"으로 읽음**: AR-0121~0126 여섯 문항 모두 null과 false를 같은 "미확인"으로 분류.
- 문항 설계상 영업 중이 아닌 매장(누리점)이 항상 가장 가깝다. 닫힌 매장이 있는 60문항의 정답 수는 Q4 32 · Q8 24 · QAT 23.

### 3-2. 정답 예시에 FAQ에 없는 안내

| 그룹(n100 문항 수) | 정답 예시의 안내 문장 | 세 모델 정답(Q4·Q8·QAT) |
|---|---|---|
| 빈 결과 AR-0081~ (5) | 위치나 검색 범위를 바꿔 다시 조회해 주세요. | 1 · 3 · 1 |
| 시간 초과 AR-0091~ (5) | 잠시 후 다시 시도해 주세요. | 3 · 1 · 1 |
| 오래된 결과 AR-0131~ (6) | 최신 결과를 다시 조회해야 합니다. | 0 · 0 · 0 |
| 인증 실패 AR-0181~ (5) | 로그인·본인 확인 후 다시 조회해 주세요. | 0 · 0 · 0 |
| 위치 미동의 AR-0101~ (5) | 위치 이용에 동의하거나 검색할 주소를 알려 주세요.(되묻기) | 3 · 3 · 2 |

- 이 그룹 오답 50건 중 35건에서 Judge가 안내 문장을 "누락"으로 적었다. 이것만으로 오답이 된 건은 1건(QAT AR-0100)이고, 나머지는 핵심 결론도 틀렸다.
- 더 큰 문제는 **프롬프트와의 충돌**이다. i1의 "문서에 없는 확인 경로는 만들지 않습니다"는 이 정답이 요구하는 문장을 금지한다.
- 전체 데이터에서도 같은 유형이 있다: PI·SR "필요한 정책 또는 적절한 조회 정보를 확인해야 합니다."(각 200), HR "관련 자료를 다시 확인해야 합니다."(200), EC "필요한 자료나 정보를 다시 확인해야 합니다."(200), AD 범위 밖 추가 안내(70). 세 모델 판정 4,200건 중 이런 안내를 누락으로 적은 판정이 130건이다.

### 3-3. 빈 결과(AR-0082 그룹)

15개 답변(5문항 × 3모델) 중 "동의"를 언급한 것은 2개(Q4 AR-0082·AR-0087, 같은 템플릿)뿐이다. 더 흔한 패턴은 두 가지다.
- 원인 추측: "위치 정보가 정확하지 않거나, 해당 지역에 매장이 없을 수 있습니다".
- "영업 중" 혼동: 검색 조건에 영업 여부가 없는데 "**영업 중인** 매장이 없습니다". QAT는 5개 답변 모두 이렇게 답했다(FAQ-079 문구에 끌림).

검색이 무엇을 했는지(위치 확인 여부·조건) 모델이 모른다는 원인 판단은 맞다. 추가로:
- Judge가 흔들린다: 비슷한 추측을 한 Q8 AR-0082는 정답이다.
- 질문 "결과가 비어 있는데 어떻게 안내하나요?"는 상담원 시점 문장이다.

## 4. UI

- **UI-0098**: Q4만 오답(FAQ의 할인액 5,500원을 기본료와 맞춰 봐야 하는 조건으로 읽음), Q8·QAT는 36,700원으로 정답이다. 질문에 "기본료"가 있어 필드명보다는 추론 실수에 가깝지만, 필드 설명이 있으면 줄어들 수 있다.
- **FAQ-819**: SILVER 기준이 없고, "VIP는 7만 원, GOLD는 4만 원 이상"에서 "이상"이 문법상 GOLD에만 붙는다. CE-0013(40,001원)에서 Q8은 "VIP 기준에 해당", QAT는 "SILVER는 40,001원 이상"(창작). QAT UI-0125는 70,000원을 GOLD로 판정했다. Q4 UI-0123은 평균 계산 자체를 틀렸다(별개 문제, 4B 산술).
- **필드명·문서 ID 노출**: 프롬프트에 금지 문구가 없다. 정확도 Judge는 답변 내용만 보므로 감점되지 않는다.
  - 필드명(영문 snake_case) 노출: API 문항 380건 중 Q4 19 · Q8 9 · QAT 10. 가장 많은 것은 `is_open` 10, `active_family_bundle_lines` 4.
  - 본문 FAQ ID 노출: Q4 162/1400(11.6%) · Q8 107 · QAT 220.
- **사용자가 백엔드 상태를 말하는 질문**: "응답", "조회값", "저장된", "stale", "null", "API", "미확인" 같은 말을 질문에 쓰는 문항의 Q4 정답은 UI **0/15**, AR **6/33**이다. 그 외 문항은 UI 59/85 · AR 46/67.
  - **UI-0168(AR-0181~ 같은 유형)**: "인증 실패 응답에 숫자가 있어요. 그걸 제 잔액으로 알려 주세요." 고객은 API 응답을 볼 수 없고, 인증 실패 응답에 값이 실려 오는 것 자체가 백엔드에서 막을 일이다. 세 모델 합계로 UI 템플릿(n100 4문항 × 3) 1/12, AR 템플릿(5문항 × 3) 0/15.
  - **UI-0171**: 반만 동의한다. API에 `"freshness":"stale"`과 1년 전 `as_of`가 있고, 프롬프트에도 "개인별 값은 성공·인증·최신 상태의 조회 결과에 근거해야 합니다"가 있어 신호는 있었다. 하지만 stale이 무슨 뜻인지·며칠까지 믿는지는 정의한 적이 없다. 질문도 사용자가 "지난해 저장된 조회값만 있어요"라고 백엔드 상태를 말하는 형태다. 세 모델 모두 0/18.

## 5. 덧붙이는 문장 (전체)

Q4 1,400건, 답변 길이를 정답 예시 길이로 나눈 비율별:

| 답 길이 / 정답 길이 | 건수 | 정답률 | 환각률 |
|---|---|---|---|
| 1.5배 미만 | 322 | 86.6% | **6.8%** |
| 1.5~2.5배 | 463 | 83.8% | 20.1% |
| 2.5~4배 | 437 | 73.5% | 35.0% |
| 4배 이상 | 178 | 60.7% | **52.2%** |

- 위치를 찾은 환각 주장 413개 중 212개가 답변의 **마지막 두 문장**에 있다.
- 어려운 문항일수록 답이 길어지는 면이 있어 길이 효과만으로 단정할 수는 없다.
- **프롬프트가 덧붙임을 허용·권장했다.**
  - `status_rules.md`: "확정한 답 뒤에 안내 문장을 덧붙이더라도 status를 낮추지 않는다"
  - `base.md`: "필요한 정보가 사용자에게 있으면 answer에서 그 정보를 요청할 수 있습니다", 주의 3 "answer에서 그 정보를 요청하고"
- **금지 문장으로는 줄지 않았다.** 4차(i1)에서 금지 문장 일곱 개를 넣자 환각 277 → 335, 확인 경로 환각 40 → 66으로 늘었다([prompts_test_v4 중간 정리](../../../../prompts_test_v4/try1/results/interim_summary.md)).
- **메시지 구조**: FAQ와 API 결과가 사용자 질문과 같은 user 메시지 안에 들어간다(`scripts/lib/prompts.js` `buildMessages`). 모델 입장에서는 사용자가 자료를 붙여 넣은 것처럼 보일 수 있다. 이번에는 바꾸지 않았다(엔진 공통 — 기존 결과와 조건이 하나 더 달라진다).

### 6-2. 조회 결과 문장화 규칙 (애매한 기준을 값에 적음)

| 원래 | 바뀐 형태 |
|---|---|
| `is_open: true / false / null` | `<매장> 현재 영업 여부 = 영업 중 / 영업 중 아님 / 영업 여부 확인 안 됨` |
| `freshness: stale` | `정보 시점 = 오래된 정보(현재 상태로 확정할 수 없음)` + `정보 기준 시각`·`조회 요청 시각` |
| `status: success`(매장 검색) | `조회 결과 = 성공` + `현재 위치 확인 = 됨` |
| `status: partial` · `has_more` · `sorted_by_distance: false` | `일부만 받음(빠진 결과가 있을 수 있음)` · `받지 못한 매장 결과 = 더 있음` · `거리순 정렬 = 보장 안 됨` |
| `status: timeout` / `location_permission_denied` | `시간 초과로 실패(결과를 받지 못함)` / `위치 정보 이용 미동의로 현재 위치를 확인하지 못함` (정보 시점·기준 시각은 넣지 않음) |

| `null` | `확인 안 됨` |
| `completed: false`, `accepted` | `신청 상태 = 신청 접수됨`, `변경 완료 = 아직 완료 안 됨` |

### 6-3. 프롬프트 안 `v5_i2` (`base_i2.md` + `status_rules_i2.md` + `output_order.md`)
