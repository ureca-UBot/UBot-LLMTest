# 프롬프트 3안 설계 근거

대상: `qwen3:14b` (temperature 0, 추론 off) · 프롬프트만 바꾸고 나머지 조건은 test3 추론 off 라운드와 동일
근거 자료: [results/test3/ai_analysis.md](../../results/test3/ai_analysis.md) 13.1~13.2절, `ec2-linux_qwen3-14b_t0_nothink_20260920` 생성 결과 집계

## 1. v0의 약점 — 무엇을 고치려는가

전체 기대 상태 일치율은 79.3%인데, 특정 유형에 몰려서 틀린다.

| 유형 | n | v0 일치율 | 어떻게 틀리는가 |
|---|---:|---:|---|
| 유사하지만 답 없음 | 35 | **28.6%** | ABSTAIN→CLARIFY 14건, ABSTAIN→PARTIAL 11건 |
| API 결과 답변 | 5 | 40.0% | PARTIAL→ANSWER (조회 결과에 없는 항목까지 확정) |
| 무관 FAQ | 20 | 60.0% | ABSTAIN→OUT_OF_SCOPE 8건 |

원인은 셋으로 갈린다.

**① 값이 없는데 일반 설명으로 대신 답한다.**
```
SR-0006 "약정 해지 위약금이 정확히 얼마인가요?"   (컨텍스트에 금액 없음)
v0: "계약 조건에 따라 달라질 수 있습니다. 구체적인 금액은 고객센터에서…"  → PARTIAL (기대 ABSTAIN)
```

**② 내용은 맞는데 되물어서 CLARIFY로 분류한다.**
```
SR-0016 "가족 데이터 공유는 최대 몇 명까지 되나요?"
v0: "제공된 자료에 명시되어 있지 않습니다. 보다 구체적인 정보를 드리기 위해 추가 확인이 필요합니다."
    → CLARIFY (기대 ABSTAIN). 사용자가 무엇을 알려줘도 자료에 값이 없으므로 되물을 일이 아니다.
```

**③ 자료가 없는 이유를 지어내고 범위 밖으로 처리한다.**
```
HR-0005 "우리 동네 기지국의 정확한 주소를 알려주세요."
v0: "기지국 주소는 통신사의 내부 정보로 외부에 공개되지 않습니다."  ← 자료에 없는 주장
    → OUT_OF_SCOPE (기대 ABSTAIN). 통신 주제인데 자료가 없을 뿐이다.
```

v0 프롬프트는 "근거 없는 내용을 만들지 마라"고는 하지만, **status 6종의 경계를 정의하지 않는다.** 그래서 모델이 "모른다"를 CLARIFY·PARTIAL·OUT_OF_SCOPE 중 어디에 넣을지 매번 다르게 판단한다.

## 2. 세 안의 설계

세 안 모두 **v0 전문을 그대로 두고 뒤에 블록 하나만 덧붙인다.** 한 번에 하나만 바꿔야 점수 변화의 원인을 가릴 수 있다.

| 안 | 바꾼 것 | 왜 나아질 것으로 봤는가 | 기대 효과 | 부작용 위험 |
|---|---|---|---|---|
| **v1_status_rules** (1,304자) | status 6종 경계 정의 + 주의 5개 | 판단이 흔들리는 이유가 기준 부재라면, 기준을 명시하면 ①②③이 함께 잡힌다 | 유사하지만 답 없음 · 무관 FAQ · API 결과 동시 개선 | 규칙이 길어 지시를 흘릴 수 있음. 입력 토큰 증가로 지연 상승 |
| **v2_value_guard** (977자) | 값 질문·범위 판정 규칙 2줄 | ①②가 "값이 없으면 보류"라는 한 규칙으로 덮인다. 규칙이 짧을수록 지킬 확률이 높다 | v1과 비슷한 개선을 더 적은 규칙으로 | ③(API 결과)은 겨냥하지 않아 그대로 남음 |
| **v3_decision_tree** (1,152자) | status 판단 순서 강제 (ABSTAIN을 CLARIFY보다 먼저) | ②는 기준을 몰라서가 아니라 **CLARIFY를 먼저 떠올려서** 생긴다. 순서를 바꾸면 해결된다 | ABSTAIN→CLARIFY 14건을 직접 겨냥 | 순서를 따르다 과잉 보류 발생 가능 |

세 안을 비교하면 이것이 갈린다.
- **v1 vs v2** — 규칙을 많이 넣어야 하는가, 핵심 2줄로 충분한가
- **v1 vs v3** — 기준을 알려주는 것과 판단 순서를 정해주는 것 중 무엇이 듣는가

## 3. 주의: 기존 v2_decision_tree를 뒤집었다

이전 안의 판단 순서는 CLARIFY를 ABSTAIN보다 먼저 봤다. 그런데 지금 실패의 절반이 **보류해야 할 문항을 되물음으로 처리하는 것**이라, 그대로 두면 악화될 설계였다. 그래서 v3에서는 ABSTAIN을 앞으로 옮겼다.

같은 이유로 이전 `v1_structured`(형식만 분해)는 버렸다. 포맷 성공률이 이미 99.7%라 개선 여지가 없다.

## 4. 판정 기준

`results/test3_prompt/prompt_test_qwen3-14b_<날짜>.md`의 **"v0 대비 개선·퇴보 요약"**을 먼저 본다. 같은 문항을 짝지어 센 개선/퇴보 문항 수다.

- 300문항에서 1문항 ≈ 0.3%p. **순증이 한 자리 수면 채택 근거로 보지 않는다.**
- 기대 상태 일치율만 보고 고르지 않는다. 보류를 남발하면 이 지표는 오르지만 답을 못 하는 상담봇이 된다 → `부재판단 F1`과 RAG 근거율의 `n`을 함께 본다.
- 지연도 함께 본다. 프롬프트가 길어지면 입력 토큰이 늘어난다. v0 기준 평균 5.51초 / P95 8.11초이고, 상담 실용선은 P95 3~5초다.
- 채택 후에는 다른 모델(`gemma3:12b` 등)에서도 같은 방향으로 움직이는지 확인한다.

실행 방법은 [PROMPT_TEST.md](PROMPT_TEST.md), 프롬프트 원문은 [scripts/test2/lib/prompts.js](../test2/lib/prompts.js)에 있다.
