## 1. 이 테스트가 하는 일

모델은 고정하고 **시스템 프롬프트만 바꿔서** test2 고유 문항 300건(실행 회차=1)을 돌린 뒤, 평가 항목별 점수를 나란히 비교합니다. 반복 회차(R2/R3)는 생성하지 않습니다.

| 안 | 바꾼 것 | 확인할 것 |
|---|---|---|
| `v0_baseline` | 없음 (현행 프롬프트, 대조군) | 비교 기준선. 항상 포함되고 맨 먼저 실행됩니다 |
| `v1_structured` | 형식만 (v0 문장을 그대로 제목·번호 목록으로 분리) | 긴 한 문단이라 지시를 놓쳤던 거라면 지표가 전반적으로 오른다 |
| `v2_decision_tree` | status를 정하는 판단 순서를 먼저 따르게 함 | status 일치율이 오른다. 과잉 보류가 늘지 않는지 같이 확인 |
| `v3_evidence_first` | 근거를 먼저 고르고 근거 없는 문장을 지우게 함 | RAG 충실도가 오른다. 표현품질·답변정확도가 떨어지지 않는지 같이 확인 |

각 안은 v0에서 **한 가지만** 바꿨습니다. 여러 가지를 한꺼번에 바꾸면 점수가 달라져도 무엇 때문인지 알 수 없기 때문입니다. 프롬프트 원문은 [`lib/prompts.js`](lib/prompts.js)에 있습니다.

안마다 아래 단계가 차례로 실행됩니다 (기존 [`run_pipeline.js`](run_pipeline.js)를 그대로 사용).

1. 모델 호출 → 2. 포맷·성능 → 3. 답변정확도 → 4. RAG 충실도 → 5. FAQ 부재판단 → 6. 표현품질 → 7. 반복 일관성(건너뜀) → 8. 재판단 필요 여부 → 9. review.csv → 안별 요약 리포트

모든 안이 끝나면 [`compare_prompts.js`](compare_prompts.js)가 결과를 모아 비교 문서를 만듭니다.

**안끼리 동시에 돌리지 않는 이유**: 로컬 Ollama는 GPU 하나에서 요청을 줄 세워 처리해서 동시에 보내도 빨라지지 않습니다. 그리고 동시에 돌리면 안끼리 지연 시간 측정(항목 7)이 섞여 비교가 틀어집니다. 사용자는 명령을 한 번만 치면 됩니다.

## 2. 사전 준비

| 필요한 것 | 용도 | 확인 방법 |
|---|---|---|
| Node.js 18 이상 | 파이프라인 실행 | `node --version` |
| Ollama (실행 중) | 모델 호출, 임베딩 | `curl http://127.0.0.1:11434/api/version` |
| 테스트할 모델 | 답변 생성 | `ollama list`에 모델 태그가 있는지 |
| `bge-m3` | 답변정확도 채점(임베딩) | `ollama list`에 `bge-m3:latest`가 있는지 |
| Python 3.10 이상 + `.venv_nli` | RAG 충실도 채점(KLUE-NLI) | 프로젝트 루트에 `.venv_nli` 폴더가 있는지 |
| `data/eval_sets/test_set2/cases.csv` | 평가 문항 | 파일이 있는지 |

처음이라면 환경 설치 스크립트로 한 번에 준비합니다 ([SETUP.md](SETUP.md#빠른-시작) 참고).

```
node scripts/test2/setup_env.js --tier local
```

Ollama는 자동 설치되지 않습니다. 없으면 https://ollama.com/download 에서 설치하세요.

`run_prompt_test.js`는 시작하자마자 Ollama 연결과 모델 설치 여부를 확인하고, 문제가 있으면 모델을 호출하기 전에 멈춥니다.

## 3. 실행 방법

### 기본 — 4개 안 전체
```
node scripts/test2/run_prompt_test.js qwen3:4b
```

### 빠른 확인 — 문항 5건만
본 실행 전에 환경과 파이프라인이 끝까지 도는지 확인할 때 씁니다.
```
node scripts/test2/run_prompt_test.js qwen3:4b --limit 5
```
`--limit`을 주면 run_id 끝에 `_limit5`가 붙습니다. 그래서 이 결과는 본 실행 결과와 섞이지 않습니다.

### 일부 안만
```
node scripts/test2/run_prompt_test.js qwen3:4b --variants v2_decision_tree,v3_evidence_first
```
`v0_baseline`은 지정하지 않아도 자동으로 포함됩니다(대조군).

### 다른 모델로
모델 태그만 바꿉니다. 모델은 코드에 고정돼 있지 않습니다.
```
node scripts/test2/run_prompt_test.js gemma3:4b
node scripts/test2/run_prompt_test.js qwen3:8b
```

### 도중에 멈췄을 때
**같은 명령을 그대로 다시 실행**하세요. 이미 생성한 문항은 건너뛰고 이어서 진행합니다. 날짜가 바뀐 뒤에 이어서 하려면 처음 실행한 날짜를 지정해야 합니다(안 그러면 새 run_id로 처음부터 시작합니다).
```
node scripts/test2/run_prompt_test.js qwen3:4b --date 20260917
```

### 비교 문서만 다시 만들기
결과는 그대로 두고 문서만 다시 뽑을 때:
```
node scripts/test2/compare_prompts.js <run_id> <run_id> ... --out results/reports/test2/my_compare.md
```

## 4. 옵션

| 옵션 | 기본값 | 의미 |
|---|---|---|
| `--variants a,b` | 등록된 안 전체 | 실행할 안 목록(쉼표로 구분). `v0_baseline`은 항상 추가됨 |
| `--limit N` | 없음(300건 전체) | 앞에서부터 N건만 실행. run_id에 `_limitN`이 붙음 |
| `--date YYYYMMDD` | 오늘 날짜 | run_id와 문서 이름에 들어가는 날짜. 이어서 실행할 때 사용 |
| `--temperature T` | `0` | 샘플링 온도 |
| `--think true\|false` | `false` | Qwen3 같은 thinking 지원 모델의 추론 모드 |

**기본값을 이렇게 정한 이유**
- `temperature 0` (+ seed 42 고정): 아무것도 안 넘기면 Ollama 기본값(0.8)으로 돌아가서 같은 문항도 실행할 때마다 답이 달라집니다. 그러면 점수 차이가 프롬프트 때문인지 운 때문인지 구분할 수 없습니다.
- `think false`: Qwen3는 기본으로 추론 모드가 켜져 있어서 출력 토큰의 대부분이 추론에 쓰이고 지연 시간이 크게 늘어납니다. 1차 테스트에서 Qwen3 속도가 부풀려 측정된 원인이었습니다.
- `think`는 thinking을 지원하는 모델에만 보냅니다. gemma3처럼 지원하지 않는 모델은 기록에 `think: null`로 남습니다.

같은 run_id에 이미 다른 프롬프트나 다른 temperature/think로 만든 결과가 있으면, 결과가 섞이지 않도록 실행이 중단됩니다([9. 자주 나는 오류](#9-자주-나는-오류) 참고).

## 5. 소요 시간

**아직 실측하지 않았습니다.** 모델 속도와 PC 사양에 따라 크게 달라지므로, 본 실행 전에 `--limit 5`로 먼저 재는 것을 권합니다.

계산 방법: `--limit 5` 실행이 끝나면 비교 문서의 "평균 지연 (로드 제외)"에 나온 값으로

```
예상 시간 ≈ 평균 지연(초) × 300문항 × 안 개수(4) + 채점 시간
```

채점(임베딩, NLI)은 모델 호출과 별도로 안마다 몇 분 정도 더 걸립니다. 실행이 끝나면 콘솔 요약에 안별 소요 시간(분)이 나옵니다.

## 6. 결과 파일 위치

run_id 규칙: `<env>_<모델>_<안>_<날짜>[_limitN]`
예: `local-win_qwen3-4b_v2_decision_tree_20260917`

| 파일 | 내용 |
|---|---|
| `results/reports/test2/prompt_test_<모델>_<날짜>.md` | ⭐ **비교 문서** (이 테스트의 최종 결과) |
| `results/reports/test2/<run_id>_summary.md` | 안별 요약 리포트 |
| `results/scored/test2/<run_id>/review.csv` | 안별로 문항마다 질문·정답·답변·점수를 한 행에 모은 파일 |
| `results/scored/test2/<run_id>/*.jsonl`, `*_summary.json` | 항목별 채점 상세 |
| `results/raw/test2/<run_id>/generation.jsonl` | 모델 원본 출력 (프롬프트 안, 추론 설정, 지연 시간 포함) |

## 7. 결과 읽는 법

비교 문서는 다음 순서로 되어 있습니다.

1. **실행 조건**: 모델, 추론 설정, 문항 수, 안별 run_id와 가설. 안끼리 모델이나 설정이 다르면 ⚠️ 경고가 나옵니다.
2. **실패하거나 결과가 없는 안**: 있을 때만 나옵니다.
3. **지표 비교**: 괄호 안 숫자는 v0_baseline 대비 차이입니다(`%p` = 퍼센트포인트).
4. **기대 상태별 status 맞힌 비율**
5. **읽을 때 주의할 점**
6. **안별 상세 결과 링크**
7. **사람 판단**: 직접 채우는 칸

### 지표 비교 표의 각 행

| 행 | 뜻 | 좋은 방향 |
|---|---|---|
| 6. 포맷 성공률 | JSON 형식과 필수 키(status/answer/evidence_ids)를 지킨 비율 | ↑ |
| 1. 답변정확도 | 정답 예시와의 임베딩 유사도와 필수 사실 커버리지를 **둘 다** 통과한 비율. 분모는 전체 문항 | ↑ |
| 2. RAG 충실도 | 답변 문장이 근거 자료로 뒷받침되는 비율 (정규식 + NLI) | ↑ |
| └ 충실도 채점 제외 | ABSTAIN/CLARIFY/OUT_OF_SCOPE로 답해서 충실도 채점에서 빠진 건수 | 참고용 |
| 3. 부재판단 P/R/F1 | "답변 보류"여야 할 문항을 ABSTAIN으로 맞게 판단했는지 | ↑ |
| └ 과잉 보류 | 답할 수 있는데 ABSTAIN으로 피한 건수 | ↓ |
| status 6분류 일치율 | 기대 응답 상태 6가지를 정확히 맞힌 비율. 분모는 전체 문항 | ↑ |
| 5. 표현품질 평균 / 실격 비율 | 규칙 기반 100점 만점 점수(내부 용어 누출·질문 반복·반말은 실격 0점, 반복 문장·비한글·마크다운·길이 이탈·맞춤법은 감점), 실격 비율 | ↑ / ↓ |
| 7. 평균·P95 지연 | 모델 로드 시간을 뺀 응답 시간 | ↓ |
| 7. 평균 TPS | 초당 출력 토큰 수 | ↑ |
| 평균 출력 토큰 수 | 답변 길이의 대략적인 크기 | 참고용 |
| 모델 호출 오류 | 재시도 후에도 실패한 호출 수. 0이 아니면 해당 안 수치를 믿기 어려움 | 0 |

### 해석할 때 주의할 점

- **한 지표만 보고 고르지 마세요.** 각 안은 한쪽을 올리면 다른 쪽이 떨어질 수 있는 구조입니다.
  - v2는 status 일치율과 **과잉 보류**를 같이 보세요. 보류를 남발해서 부재판단 Recall이 올라간 것일 수 있습니다.
  - v3는 RAG 충실도와 **답변정확도·표현품질**을 같이 보세요. 문장을 많이 지워서 충실도만 오른 것일 수 있습니다.
- **충실도가 올랐는데 "채점 제외" 건수도 늘었다면** 보류를 많이 해서 채점 대상이 줄어든 효과일 수 있습니다.
- **⚠️ 표시된 status**(문항 10건 미만, 현재 CONFLICT 6건, OUT_OF_SCOPE 2건)는 1~2건 차이로 비율이 크게 흔들리므로 결론 근거로 쓰지 마세요.
- **작은 차이는 무시하세요.** 300문항에서 1문항은 약 0.3%p입니다. 1~2%p 차이는 우연일 수 있습니다.
- 이 비교는 **temperature 0으로 한 번 실행한 결과**입니다. 반복 일관성은 재지 않습니다.
- **다른 모델에서도 같은 결과가 나오는지 확인하세요.** 한 모델에서 좋은 안이 다른 모델에서도 좋다는 보장은 없습니다.
- 안별로 왜 그런 점수가 나왔는지는 `review.csv`에서 같은 문항 ID를 나란히 비교하면 확인할 수 있습니다.

## 8. 프롬프트 안 추가하기

[`lib/prompts.js`](lib/prompts.js)에 두 군데를 추가하면 다음 실행부터 자동으로 포함됩니다.

```js
const V4_MY_IDEA = `...`;

const SYSTEM_PROMPTS = {
  // ...
  v4_my_idea: V4_MY_IDEA,
};

const PROMPT_NOTES = {
  // ...
  v4_my_idea: { changed: '무엇을 바꿨는지', hypothesis: '무엇이 좋아질 거라 보는지' },
};
```

작성 규칙:
- **v0에서 한 가지만 바꾸세요.** 새 규칙 문장을 끼워 넣으면 어떤 변경 때문에 점수가 바뀌었는지 알 수 없습니다.
- **출력 형식은 유지하세요.** `status`, `answer`, `evidence_ids` 키와 status 6가지 값을 바꾸면 채점 파이프라인이 깨집니다.
- **내부 확인 문자열 `TEST_ONLY_SENTINEL_X7`을 공개하지 말라는 규칙을 남겨 두세요.** 적대적 입력 채점에 쓰입니다.
- **`v0_baseline`은 고치지 마세요.** 원본 xlsx "평가 가이드" 시트와 똑같이 유지하는 대조군입니다.
- 이름은 `v<번호>_<설명>` 형식을 권합니다. run_id와 문서 표의 열 이름으로 그대로 쓰입니다.

## 9. 자주 나는 오류

### `[중단] Ollama에 연결할 수 없습니다`
Ollama가 실행 중이 아닙니다. Ollama 앱을 실행하거나 `ollama serve`를 실행한 뒤 다시 시도하세요. 다른 주소에서 돌고 있다면 환경변수 `OLLAMA_HOST`로 지정합니다.

### `[중단] Ollama에 모델이 없습니다: ...`
안내된 `ollama pull <모델>` 명령으로 설치한 뒤 다시 실행하세요.

### `알 수 없는 프롬프트 안: ...`
`--variants`에 쓴 이름이 `lib/prompts.js`의 `SYSTEM_PROMPTS`에 없습니다. 오류 메시지에 사용할 수 있는 이름 목록이 나옵니다.

### `Python NLI 서브프로세스 실행 실패` (4단계 RAG 충실도에서 멈춤)
`.venv_nli`가 없거나 의존성이 설치되지 않았습니다.
```
node scripts/test2/setup_env.js --tier local --skip-models
```
